## 二、本周仓库要长出的结构

上周结束时，`backend/` 里站着十三个 `.py`（按入仓文件计，不含被 `.gitignore` 挡住的 `check.py`），`data/` 下有六个文件（`a23.db`、`parse_result.json`、`facts_export.json`、`filled_2025中国城市经济百强.xlsx`、`fill_report.json`、`eval_report.json`；第二档同学另有三份 covid 产出，不影响本周），`frontend/` 已经从空文件夹长成一棵真有页面的树：打开 `http://127.0.0.1:8000`，选文件、点按钮、看六个数，全程不碰终端。

README 里应当有那一行数字和三条坏输入提示原文。只做到第 5 周最低完成线的人，手上可能只有 build 与启动两条命令——不影响本周，第 0 步会带你重新把那几个数算出来。

这周不新增任何业务功能，`backend/` 里已有的十三个文件一个都不改：`main.py` 的接口语义、`evaluate.py` 的比对规则、`filler.py` 的写入方式、两个率的算法，全部原样。新增两个文件，都在 `backend/` 下，都不是业务代码：一份测试、一份环境清单。`frontend/` 一行不改。

`.py` 的数一数就容易乱，先把口径说死：数的时候用 `git ls-files "backend/*.py"` 更准，`ls backend/*.py` 会多出一行 `check.py`——那不是多个文件，是第 2 周那个自测脚本，它一直没进仓库。**第一档**数出来是十三个，本周加 `test_a23.py` 是十四个；**第二档**会多出你自己起的解析器、03 那份的填写脚本与判据命令（第 2 周就说好"文件名自定"），数出来十几个到十七个都正常——以 `git ls-files` 的实际输出为准，不按十三这个数对账。`check.py` 与 `.gitignore` 里的规则都不动。

同样，`data/` 下一共会到十三个文件：第一档六个，第二档再加三份 covid 产出与四份 `facts_export_*.json`。本周一律不碰；第一档同学看到别人有十几个而自己只有六个，不是少了东西。

**跑测试之前，有一件事必须先成立：`frontend/dist/index.html` 存在。** 这不是可选项。`main.py` 在模块层把 `frontend/dist` 挂到 `/`，而测试模块要写一句 `from main import app` 交给 `TestClient`——导入的那一刻挂载就执行了，`dist` 不在，整份测试在收集阶段就报错，报的是目录不存在，指向的地方与测试毫无关系。所以顺序固定为：先在 `frontend/` 里 `npm install`、`npm run build`，再跑测试。`dist` 不进仓库，别人 clone 下来第一件事也是这个。

两个新文件都在 `backend/` 下、与 `main.py` 同级，不是随手放的：

- **测试必须和 `main.py` 待在同一层。** pytest 会把测试文件所在目录放进 `sys.path`，`import main` 才能成功；挪到 `tests/` 或仓库根，报的是 `ModuleNotFoundError: No module named 'main'`，看着像环境坏了，实际只是位置不对。
- **`requirements.txt` 记的是 Python 这套依赖。** 前端依赖由 `package.json` 管，`npm install` 装它；两套各管各的，不要合成一份。

各路径的职责（每个文件只干一件事）：

| 路径 | 职责 | 不该做的事 |
| --- | --- | --- |
| `test_a23.py` | 把已经认可的数字、状态码、字段名写成断言，改动后自动报错 | 不调模型、不改业务文件、不连真实网络 |
| `requirements.txt` | 记下当前环境的包与版本，供别人重建 | 不写本机绝对路径、不写指向本地的 `-e`；除本机路径行外不手工删行 |
| `README.md` 的「交接须知」 | 让没参与过的人不问你就知道怎么接手 | 不重复「怎么跑」那一节已经写过的东西 |
| `data/` | 只读的参照物，断言比它 | 测试里不改它任何一格、不覆盖任何一份报告 |

三条约定，后面几节都要用：

1. **测试只打"只读接口 + 坏输入"。** 六个接口分两类：`/health`、`/reports`、`/files` 只读，怎么测都不留痕；`/parse`、`/extract`、`/fill` 有代价——`/fill` 会重写 `filled_2025中国城市经济百强.xlsx` 与 `fill_report.json`（这是它的职责），一旦跑过，`data/` 就不再是你断言的参照物；`/extract` 要调模型、花钱、等几分钟。所以 `/extract` 与 `/fill` 只测坏输入：后缀不支持、文档名不存在、字段名不全。`/parse` 按第 2 周的写法只返回、不落盘，可以正常测——第 3 步就靠它断那 113 块；如果你后来改过它，先自己确认一遍它确实不写文件。
2. **测试不改文件。** 一次测试跑完，`data/` 下那几个文件、`doc/` 下模板原件、两个率，都应当与跑之前一模一样。要造坏输入，造在临时目录里，跑完删掉。
3. **断言里的数字是"当时认可的数"。** 具体是五个：行数、写入格数、空着的格数、单元格准确率、行完整率（第 5 周页面上多一列耗时，所以那边叫"六个数"，指的是同一批数）。它们来自第 4 周终端那一行、第 5 周页面上的数，不是天上掉的。耗时不算在内——它只记量级，同一件事这台机器上 1.8 秒、下次 2.3 秒都正常，把它写成断言，你每天都会收到一次假警报。将来换了文档或改了规则，要同时改断言；这道摩擦是有意留的，它提醒你"数字变了"这件事本身需要解释。

关于本周多出来的那个包：跑测试用 pytest。它在六周的技术栈清单之外，是本周唯一一处例外，范围只到测试——`fastapi dev main.py`、`npm run build`、页面演示，没有一处需要它，业务代码也不许 `import pytest`。它会出现在 `requirements.txt` 里，这是对的：别人要跑你的测试，就得装上它。技术栈那条约束本身不为这一处松动，写文档、写给评审的说明里，仍按原来的六项陈述。

顺带一句，免得你数包时多心：`TestClient` 依赖 `httpx`，第 2 周装 `fastapi[standard]` 时已经带上了（新版里这个依赖可能叫 `httpx2`，清单里出现哪个都正常）。别删它。

pytest 跑完会在原地留一个 `.pytest_cache/` 目录，里面是上次运行的中转文件，不该进仓库。本周改 `.gitignore` 只有这一处：在现有规则末尾追加一行 `.pytest_cache/`，已有的规则一条不动（第 5 周允许补过 `dist/`，那份也是已有的）。

两个新文件有没有被 `.gitignore` 挡住，交之前各查一次：`git check-ignore -v backend/test_a23.py` 与 `git check-ignore -v backend/requirements.txt`，两条都**没有输出**才算过。有输出就说明命中了某条整类规则，照着它给的行号去看是哪一条。

# 引导和说明：

上周结束的时候，我们手上有六个数、两份能解释它们的报告、一张点得开的页面。打开 `http://127.0.0.1:8000`，选一份 docx，点几下，数字出来，表能下载——你不用在旁边解说，对方也能走完一遍。这是第 5 周真正拿到的东西。

但"能演示"和"能交接"还差一层。差的那一层不是文档写得不细，是**你没法证明它还是对的**。

先别急着动手，把六周摊开看一眼，知道这周站在哪儿：

| 周             | 这周把什么变成什么                          |
| ------------- | ---------------------------------- |
| 第 1 周         | 环境与仓库：代码进得去仓库，别人看得懂                |
| 第 2 周         | 文件 → 统一数据：多格式进，一个 schema 出         |
| 第 3 周         | 文本 → 结构化事实：抽出事实，每条都说得出出处           |
| 第 4 周         | 数据 → 交付物：填进模板，并报得出可核对的数字           |
| 第 5 周         | 后端 → 能用：接上界面，整条链路能演示               |
| **第 6 周（本周）** | **能跑 → 能交接：测试、复现、交给别人接手**         |

这张表最后一行是六周里唯一一行不含"新东西"的：这周不加功能、不加接口、不加页面，只做验证与交接。听上去像收尾，实际是六周里最容易做假的一周——"我测过了""我复现过""文档写了"，这三句话都很好说，也都很难验。所以本周的判据不是"你说了什么"，是"别人照着你留下的东西走一遍，能不能得出同样的结论"。

那这周具体干什么？一句话：**把已经认可的数字钉成会自动失败的检查，再把"怎么从零走到这些数字"写成别人照着能走完的东西。**

可以先想两个场景，第二个这周就会发生。

第一个，六周里一定会遇到。比赛提交前一周，你打开 `fill_spec.py`，想把某一列的别名补一条。改动只有一行，改完跑一遍 `check_fill.py`——数字好像还是那几个。可你真的逐位比过吗？第 4 周你比过，那是两周前；中间你动过 `main.py`，第 5 周又动过 `check_fill.py` 里报告的外层。这一次你没有比，你只是"看着差不多"。

第二个。你把仓库地址发给同学，他 clone 下来、装依赖、起服务，然后问你："表头是不是要我自己建？""为什么页面上没有数？""你说的 500 格，我这显示 0。" 三个问题都不是他笨，是你的说明里没写"从零到有数"这条路上的三个坑。

所以这周的产出不是新功能，而是两样能交出去的东西：**一份谁都跑得起来的测试文件，和一节照着走就能重建的交接说明。**

打个比方。前五周你一直在造一台机器，并且亲手试过它能转。这周做两件事：在机器上装一排指示灯，以后哪个零件松了灯就红；再写一张操作卡，别人不用懂这台机器，照着卡片也能开机、也能看出红灯代表哪里松了。

这周还有个新情况，和前五周都不一样：**前五周证明的是"它做出来了"，这周要证明的是"它没被改坏"。** 做出来看得见，没被改坏看不见——所以这周的活，大半不在写新代码上。

**本周只有一个新概念：回归测试。**

说清楚就一句话：**把你已经确认过的事实写成断言，以后每次改动，机器替你重新确认一遍。**

对比一下前几周的"验证"就明白了。第 4 周你已经有一个 `evaluate.py`，它会逐格比对、算出两个率——但那是"你手动跑一次、你看一眼结果"。第 5 周更依赖人眼：打开页面，看那六个数在不在、像不像。人看一眼就过去了，下次改动还得再看一遍，而且多半不会看。这周你把这句话写下来：第 2 行第 2 列是数值，等于 56708.71。写下来之后它就一直在那儿——你改 `fill_spec.py`、改 `filler.py`、改抽取的批大小，跑一条命令，它会告诉你哪一条不再成立。

三个东西够用一整周：一条断言（`assert`）、一个测试文件（`test_a23.py`）、一条命令（`pytest`）。不需要夹具、参数化、覆盖率报告——那些是给几十个模块的项目用的，你这里只有一个文件、二十来条断言。

听上去省事，代价是它只守"变没变"，不守"对不对"。断言里的数是你在第 4、5 周认可过的数。如果那个数本来就错，测试会把错的牢牢锁住——以后每次改动，它都照样说"通过"。所以这周的第一件事不是写断言，是先想清楚"我要锁哪几个数、凭什么认为它们是对的"。这件事没有唯一答案，第 2 步会给你一张表让你自己填。

这周真正要你自己拿主意的地方，是**哪些数必须一模一样、哪些只要落在区间里**。分两类有个抓手：看这个数是怎么来的。

只由文件和模板决定的那几个，换个目录重跑也应当一位不差。中间过了模型的那几个，换个库就得重抽，而重抽一次结果就可能不同——第 3 周就写过"同一段话两次调用，措辞可能不同"，那一周因此只比条数和值，不比整段文字。这条老经验，这周要落到判据上。

于是同一条链路上会同时存在两把尺子，按场景分：**同一台机器、同一个库、不重抽**，五个数仍按第 5 周的标准逐位比；**换目录、重建库、必须重抽**，五个数里只有行数还站得住（它由第 4 周第 4 步那三层段落判据决定，与模型无关），其余四个落在你定的区间里。区间定多宽、凭什么定，由你定，但定了要能被第三个人照着复算。

还有一个坑，本周会反复出现：**测试跑在哪个目录、`dist` 在不在，决定它能不能起来。** `main.py` 在导入时就把 `frontend/dist` 挂到 `/`，`dist` 不在，测试连收集都过不去，报的还是一句与测试无关的目录错误。上周你只在"起服务"时遇到这个前置，这周它在"跑测试"时又来一次。

**这周不做什么。** 记住一句就够：这周只做验证与交接，不负责"把系统再做大一点"。不加接口、不加页面、不改比对规则、不改映射表、不做性能优化、不做前端测试（前端本周一行不改，也就没有可测的东西）、不接 CI 与自动化流水线。也不重修前五周的产出：`evaluate.py` 与 `filler.py` 的规则一行不动，动的是"怎么检查它们"，不是"它们怎么算"。

另外，第 5 周已经把耗时单独按"量级"处理，这周要拆的是余下五个。拆成几类、每类按什么判，是第 2 步那张表的事，这里只提醒一句：五个都要求逐位，测试会在你换环境那天集体变红，最后你把整份测试注释掉——那比不写更糟。

**关于两档。** 第一档做一条能自检、能复现、能交接的链路，步骤和命令写全，照着做就能交。第二档两段都做：先照第一档完整走一遍，交付物与标准一条不减，再做第二段的增量——那一段撤掉步骤，只给目标、方向和验收标准。方向是**判据可机器判定**：第一档你证明"我能复现"，第二档要求"别人不必读你的代码，只跑一条命令、看一张表，就能判定你对不对"。判据从哪来、阈值凭什么定、失败时该说什么，都由你定，但定了要能被第三个人照着复算。

**怎么算这周做成了？** 不看"我写了测试"，看三件事：

1. 一条命令跑完就出结果；故意改坏一个数，它会失败，并且指出是哪一条不成立——这一条要真的做一遍，不是说"应该会"。
2. 换一个目录重建一遍，照 README 走到页面出数，五个数与你原来那台机器对得上——哪些逐位、哪些落在区间里，按你第 2 步定的口径。

3. 交换仓库的同学只看你的 README，能走到六个数出现，并且能回指某一条说清：它是逐位比还是落在区间里，这个口径从哪来。

三条都很朴素，但总规划里"能交接：没参与过的人只看文档能接手，并复现同样的数字"就是这么验的。总规划只排到第 6 周，这三条成立，六周才算闭合。

最后说时间与心态。这周会第一次出现"我写的测试拦住了我自己"的情况：你改了一处本以为无关的地方，测试红了，去查，发现确实改坏了——这半小时就是它该花的地方。也会出现另一种：测试全绿，但你心里知道它其实什么都没验（断言写的是 `assert True`，或者断言的对象早就被跳过）。后一种更危险，而这周唯一能防它的办法是第 4 步那个动作：**故意改坏，看它是不是真的会红。** 不做这个动作，你永远不知道自己的测试有没有在工作。

**卡过半小时就停下来**，按文末「卡住怎么办」把"哪一条断言红了、期望值是什么、实际值是什么、我跑的是哪条命令"整理清楚再问。这四样凑齐，问题基本一眼能看出来。前三周拼的是"能不能跑通"，第 4、5 周拼的是"跑出来的数对不对"，这周拼的是"敢不敢把判据写死"。

还有一句前五周说过、这周最要紧的：可以让 AI 帮你写测试，但讲不清的断言留不下来。交叉验收时对方会指着某一条问"为什么这个数是 500 不是 501"，你得说得出它的来历——它来自哪次运行、哪个接口、哪个文件。

这周的产出会原样成为别人接手你的入口：比赛提交前，评审看的是 README 的第一屏；队友接手时，先跑的是你那条测试命令。这周图省事，把断言写成"和上次差不多"、把交接文档写成"见代码"，第 6 周之后没有人能替你解释这些数从哪来，返工的只能是你自己。

# 第六周任务（第一档 · 引导档）

## 目标

第一档要做成的事只有一件：**把已经认可的数钉成会自动失败的检查，并让另一个人照着你的说明重建出同样的结果。**

具体到可以检查的程度，是三条：

1. 一条命令跑完整个后端检查，改坏一个数它会红，并指出是哪一条。
2. 换一个目录重走一遍：不重建库时，两个率与原来一致；重建库时，行数逐位相同、其余落在你声明的区间里。
3. 交换仓库的同学只看 README 能走完，并说得出哪些数是逐位比、哪些落在区间里。

## 任务清单

先把路线说清楚：

对账 → 锁环境 → 定判据 → 测只读接口 → 钉住五个数 → 换目录重建 → 写交接说明 → 交叉验收 → 留证。

九步里，第 0 步是对账——先把参照的数重新抄一遍，后面每一步都要拿它对；第 1、2 步是准备；第 3、4 步是本周的新东西；第 5 步是这周真正花时间的地方；第 6、7 步把它变成别人能用的东西；第 8 步留证收尾。

这一档仍然不给成品代码，只给每个文件要做什么、断言检查什么、怎么验证。第 3 步给一段骨架，只帮你把"导入、客户端、上传"三样摆对位置。

### 第 0 步：进环境，把五个数重新抄一遍

六件事，按顺序做：回仓库根 → 激活环境 → 装 pytest → 跑一次填写脚本抄数 → 确认 `dist` 在 → 打开页面看一眼。

**第一步：把终端切到仓库根目录。** 与前五周一样，环境建在仓库根，在别处激活会找不到。

**第二步：激活你第一周建的那个环境。** 判断标准只有一个：提示符最前面出现环境名。

**第三步：进 `backend/`，装 pytest。** 这是本周唯一新增的包，命令去 PyPI 上找。装完 `pytest --version` 应当有一行版本号——注意它打印的是版本，不需要你先有测试文件。

**第四步：跑一次 `python check_fill.py`，把那行数字抄下来。** 它打印行数、写入格数、空着的格数、两个率、A 列一致行数、耗时。**空着的格数取 `/fill` 返回的 `cells_empty`**（第 4 周接口规格里就有这一项），不要用 500 减写入格数去反推：那份文档恰好填满，减法看不出区别，换一份有拒填格的就对不上。在 01 这一份上，它恒等于 500 减 `cells_written`，可以拿来做一次交叉核对——只对 01 成立，别把这个关系带到 03 那份（17794 格）。

抄的时候注意三件事：

- **耗时只记量级**，比如"两秒上下"。它不进断言，抄它只是为了第 5 步比对时有个参照。

如果 `data/eval_report.json` 不存在——第 4 周的最低完成线没把这份报告列进去，只到那条线的人手上就没有它——上面那条命令会顺手把它生成出来，不用回第 4 周补。生成之后打开看一眼：`doc`、`rows`、`cells_written`、`cells_empty`、`cell_accuracy`、`row_completeness` 六个键都要在。少一个，第 3、4 步按名字取键会全部落空，而报错只说 `KeyError`，看不出是报告的问题。

**第五步：确认 `frontend/dist/index.html` 存在。** 这一步不能跳。`main.py` 在导入时就把 `dist` 挂到 `/`，测试一构造客户端就要导入 `main`；`dist` 不在，整份测试在收集阶段就报错，报的是目录不存在，和测试本身毫无关系。不在就先在 `frontend/` 里 `npm install`、`npm run build`。

**第六步：起服务，打开 `http://127.0.0.1:8000`，看一遍六个数。** 只看一眼，确认它与第四步抄下的一致，然后关掉。这周不靠页面验证，但页面坏了你会以为是测试坏了。

**做完你应该看到**：五个数抄在一张纸上或一个临时文件里；`pytest --version` 有输出；`frontend/dist/index.html` 在；页面能打开、六个数都在。

### 第 1 步：把环境钉下来

前五周的依赖清单散在同一份 README 的各次追加里，谁也没法照它装出和你一样的环境——写的是"装了哪些包"，没写版本。这周补上这一件：把当前环境写成一份清单。

在 `backend/` 下、**激活状态里**执行一条命令，把当前环境的包与版本写到 `requirements.txt`。命令是 pip 的标准用法，自己去官方文档查（关键字：freeze、requirements）。

三个要点，每一个都对应一种失败：

- **先装齐，再导出。** 顺序反了，pytest 就不在清单里；别人照清单装完，跑测试会报 `command not found`。这也意味着**以后每装一个新包，都要重新导出一遍**。
- **清单会比你想的长，别删。** `fastapi[standard]` 一次带进 uvicorn、pydantic、python-multipart 等一串，导出的是"当前环境里有什么"，不是"你在代码里 import 了什么"。手工删掉看起来"没用"的行，别人装完就是起不来。
- **导出后打开看一眼，确认没有本机路径。** 正常的一行长这样：`fastapi==0.x.y`。如果某一行里有盘符、有 `/Users/`、有 `@ file:///`，或者 `-e` 后面跟的是一个本地目录，那是从你本机装的包，别人机器上没有那个路径，装到一半就会失败。有就删掉那一行——这是唯一允许删的情况。`-e` 后面跟 `git+https://...` 的不算：那种能从网上重装，可以留。

**做完你应该看到**：`backend/requirements.txt` 存在；里面能搜到 `fastapi`、`python-docx`、`openpyxl`、`python-dotenv`、`pytest`，以及 `httpx` 或 `httpx2` 之一。最后这一项要看版本：测试客户端依赖的 HTTP 库在两个版本里换了名字，装 `fastapi[standard]` 时可能带上其中一个、也可能两个都带上，以你的清单里实际出现的为准，不用单独装，也不必为了凑这一项去装另一个。另外注意 `python-docx` 与 `python-dotenv` 这两个：包名带连字符，代码里 `import` 时不带。

### 第 2 步：把"哪些数逐位、哪些给区间"定下来

这一步不写代码，只写一张表。它是本周最需要判断的地方，也是第 5 步和第 7 步唯一的依据。

为什么不能一概而论：这条链路上有两种数。一种由文件和模板决定——同一份 docx、同一张模板，换台机器、换个目录，结果应当一位不差。另一种中间过了模型：库里的每一条事实都是模型读出来的，换个库就得重抽，而第 3 周已经写过"同一段话两次调用，措辞可能不同"。两类数用同一把尺子量，必然有一类天天误报。

所以表要按**场景**分两列。同一台机器、同一个库、不重抽，是一列；换目录、重建库、必须重抽，是另一列。同一个数在两列里可以有不同判据，这不是双重标准，是两件事。

把下面这张表抄进一个临时文件；"换目录重建"那一列里写着"区间"的几行，你要把上下界填出来，依据看"为什么"那一列。逐位那几行不用填数，但要能说出凭什么它不必有区间。

| 数 | 从哪来 | 同机、不重抽 | 换目录重建 | 为什么 |
| --- | --- | --- | --- | --- |
| 113 块 | `POST /parse` | 逐位 113 | 逐位 113 | 只读段落，同一份文件必得同一结果 |
| 行数 | `POST /fill` → `rows` | 逐位 | 逐位 | 由第 4 周第 4 步那三层段落判据决定，不经模型 |
| 写入格数 | `POST /fill` → `cells_written` | 逐位 | 区间 | 取决于库里有几条可用事实，重抽就会变 |
| 空着的格数 | `POST /fill` → `cells_empty` | 逐位 | 区间 | 同上，跟着写入格数走；01 上它等于 500 减 `cells_written`，可自校验（03 不适用） |
| 单元格准确率 | `GET /reports` | 逐位 | 区间 | 报告由 `evaluate.py` 比出来，值取决于填进去什么 |
| 行完整率 | `GET /reports` | 逐位 | 区间 | 同上 |
| 耗时 | 页面自己计时 | 量级 | 量级 | 机器负载不同，两秒与三秒都正常 |
| 抽取条数 | `POST /extract` | 不进测试 | 不进测试 | 调模型、花钱、分钟级，理由见前文第 1 条约定 |

填"区间"那几格，不是随手写个上下界，要能回答三个问题：

- **上下界从哪来。** 你手上有几次实测？如果只有第 4 周那一次，就在备注里写"一次实测，区间为估计"，别装作测过三次。
- **区间外算什么。** 落在区间外只有两种处理：要么是这次抽取真的变差了（该查，不是该放宽）；要么是区间定错了（该改区间，并写下为什么改）。
- **谁来复算。** 换个人拿到你的表和他的数，能不能独立判断"在"还是"不在"。判不了，说明区间写得不够具体。

两条附加要求：

- **每个数都要写清"跟谁比"。** "准确率 0.94"不是判据，"`GET /reports` 返回的 `cell_accuracy` 等于我这份 `eval_report.json` 里的 0.94"才是。
- **表先写在一处，最后搬一次。** 这一步先写进一个临时文件——还没到动 README 的时候，第 6 步才写它；写测试时期望值照这份表抄，两边必须一眼对得上。第二档会要求把这件事做成机器可判定的，现在先做到"能对上"。

**做完你应该看到**：一张八行的表，每行三个判断都填了；"换目录重建"那一列里，逐位与区间各有几行，你能说清凭什么这么分。

### 第 3 步：写测试文件，先只测只读接口

新建 `backend/test_a23.py`。第一版只测不写文件的那几个入口——它们怎么测都不留痕，跑一百遍 `data/` 也不变。

六个接口分两类，先认清：

| 接口 | 会不会留痕 | 能不能进测试 |
| --- | --- | --- |
| `GET /health` | 不读库、不读报告 | 能，随便测 |
| `GET /reports` | 只读 `eval_report.json` | 能 |
| `GET /files` | 只读 `data/` 下的文件并发出 | 能 |
| `POST /parse` | 按第 2 周的写法只返回、不落盘 | 能（若你改过它，先自己确认一遍） |
| `POST /extract` | 调模型、写库、花钱、分钟级 | 只测坏输入 |
| `POST /fill` | **重写 `filled_*.xlsx` 与 `fill_report.json`** | 只测坏输入（它会刷新你的参照物） |

`/fill` 那一行是本周最容易踩的：它是唯一一个会覆盖你参照物的接口。测它一次，`filled_*.xlsx` 与 `fill_report.json` 就变成新的了——`eval_report.json` 不会被它更新（第 5 周说过），但参照物已经动了一角。这不是说它不能测，是说**测它就得接受参照物被刷新**，而本周要的是"参照物不动"。

四个细节，每个都会让一条断言假通过或假失败：

- **`TestClient` 不需要起服务。** 它在进程内直接调用应用，所以跑测试时不用先 `fastapi dev`；但也正因为如此，测试模块顶层那句 `from main import app` 在收集阶段就导入了 `main`，挂载 `dist` 这个副作用会真实发生。

### 第 4 步：把五个数钉成断言，然后故意改坏

第 3 步测的是"接口还在不在"，这一步测的是"数还是不是那几个"。五条，都读 `GET /reports` 与 `data/eval_report.json`，不碰库、不写文件——它们不依赖 `a23.db`，所以新克隆的仓库里也能跑（`dist` 仍要先 build，那是 `import main` 的前提，不是这几条断言的前提）。

按第 0 步抄下的数写：

| 断言 | 期望值从哪来 |
| --- | --- |
| `rows == 你抄下的数` | 报告里的 `rows`。这份文档是 100；只到第 4 周最低完成线的人可能不是，一律以你第 0 步抄下的为准 |
| `cells_written == 你抄下的数` | 报告里的 `cells_written` |
| `cells_empty == 你抄下的数` | 报告里的 `cells_empty`。01 上它还应当等于 500 减 `cells_written`，可用这一条做交叉核对；03 是 17794 格，那个减法不成立 |
| `cell_accuracy == 你抄下的数` | 报告里的 `cell_accuracy` |
| `row_completeness == 你抄下的数` | 报告里的 `row_completeness` |

顺带说清一个容易混的数：`rows` 是**数据行**，这份文档是 100；第 4 周那份 Excel 是 101 行，多出来的一行是表头。写断言时用 100，不是 101。

三条写法上的提醒：

- **两个率按数值比，期望值从文件里原样复制。** 读回来是 `float`，用 `==` 与字面量比通常成立；不放心就用 pytest 的近似比较（关键字：approx）。但有一点比写法更要紧：**期望值不要抄页面上显示的两位小数**。页面显示 `0.94`，`eval_report.json` 里可能是 `0.9432`，照页面抄，这条断言每天都会红，而你查半天查不出原因。**不要**先把它们格式化成字符串再比——`0.9` 与 `0.90` 也会让你莫名其妙地红。
- **`cells_empty` 要单独断一条。** 主判据是它等于报告里那个字段；01 上再顺手核一次它等于 500 减写入格数，作副判据。两个都对，才说明第 5 周改报告外层时没有算错。
- **`doc` 要断，但并进 `test_reports_ok`，不单开一个函数。** 第 5 周给 `/reports` 加了"查询参数与报告里的 `doc` 对不上就 404"这条判断。你把文档名写错一个字符，测试会得到 404 而不是数字——这一条能替你守住"页面安静地显示另一份文档的数"那个坑。并要求"两个率里的 `doc` 与它一致"，一条断言足够。

写完跑一遍，应当全绿：`12 passed`（第 3 步的 7 条，加这一步的 5 条）。**然后做本周最重要的一件事：故意改坏，看它是不是真的会红。**

改坏的办法有讲究，别改测试里那个期望值（那是自欺），改被测的东西。三步：

1. **先备份**：把 `data/eval_report.json` 复制一份到同一目录，存成 `eval_report_prev.json`，别提交，验完删掉——留着它会让 `git status` 多出一行。
2. **改坏**：把原件里的 `cell_accuracy` 改成 `0.5`，保存，跑 `pytest -q`。
3. **恢复**：拿备份盖回去，再删掉备份。

上面第 2 小步应当看到一条失败，报错里能读出"期望 0.94、实际 0.5"这类信息。用备份恢复比记着手改回去可靠——你已经改过一次数，很容易改回一个"看起来像"的值。

再验一次更狠的，验的是"结构变了会不会被发现"：临时把 `check_fill.py` 里写报告的那个键名改掉一个字母（比如 `cell_accuracy` 写成 `cell_accurcy`），重跑一次 `check_fill.py` 让报告真的变，再跑 `pytest -q`。测试应当立刻红。看完把键名改回、重跑一次 `check_fill.py`。这一条对应第 4 周说的"静默错误"：键名错了，程序不报错，只有断言会喊。

**做完你应该看到**：先 `12 passed`；改坏后至少一条 failed，报错里期望值与实际值都看得见；恢复后重新全绿。**没做过"改坏"这个动作，本步不算完成**——全绿的测试有两种，一种在工作，一种什么也没验，只有这一步能分得开。

### 第 5 步：换一个目录重建，把"能复现"验一遍

这一步是本周真正花时间的地方。目标不是"再跑一次"，是"证明它不依赖你现在这个目录"。

在仓库外面另建一个目录（不要建在仓库里面，否则 `git status` 会乱）。克隆之前先 `git push` 一次——这一步不能省：不 push，你 clone 下来的是上周的仓库，里面没有 `test_a23.py`，第 3、4 步那些测试根本不存在，"复现"就成了空跑。这也是本周第一次"先提交再验证"（第 7 步还有一次）：你验的必须是仓库里的东西，不是你磁盘上的东西。

然后把 gitee 仓库克隆进那个目录，分两级验，A 级必做，B 级选做。

**A 级：不调模型的重建（必做，1–1.5 小时）**

按顺序：建一个新环境 → 照 `requirements.txt` 装依赖 → 进 `frontend/` 装前端依赖并 build → 回 `backend/` 跑测试 → 起服务看页面。

时间大半不在装依赖上，在 `npm install` 与 build 上——这两步第一次跑都要几分钟，装完还会因为没 build 而让测试起不来。顺序不要调。

五件事会在这条路上依次撞上，每一件都不是 bug：

| 现象 | 原因 | 怎么办 |
| --- | --- | --- |
| 导入 `main` 就报目录不存在 | `dist` 还没 build | 先 build，再跑测试 |
| 页面上两个率有数，"开始填写"报"库里没有这份文档" | `a23.db` 不进仓库，新环境是空的 | 正常，这是 B 级要解决的事 |
| `/extract` 报没读到 Key | `.env` 不进仓库 | 正常，A 级不需要它 |
| 下载按钮 404 | `filled_*.xlsx` 在仓库里，但 `data/` 路径没对上 | 对照 README 里的目录约定 |
| 测试条数比原来少 | 两个原因：没 push 就 clone（新测试不在仓库里），或你在测试里写了依赖 `a23.db` 的断言，新环境没有库 | 前者先 push；后者说明那条断言本就不该写 |

A 级跑完，`pytest -q` 的通过条数应当与原目录完全一致；页面能打开、两个率能显示。**页面上的"开始填写"这时候会失败，这是对的**——`/fill` 要读库，库里没有这份文档的事实，所以六个数里只有两个率能出来。六个数整整齐齐，是 B 级做完之后的事。

**B 级：重建库再走一遍（选做，一小时起，有调用费用）**

把 `.env` 拷过去；在 `backend/` 下跑一次 `python import_blocks.py`，它调 `init_db()` 把两张表建出来；对这份 docx 调一次 `/extract`；再 `/fill`、再 `check_fill.py`。

成本要说清：这份 docx 大约十二批调用，每批都要等模型回话，中途失败重来一次，时间与费用都要再算一份。这一步的意义只有一个：证明"从零到六个数"这条路你自己走通过，不是靠一份别人给的库。

B 级的结果按第 2 步那张表看：行数应当仍是 100；其余四个（写入格数、空着的格数、两个率）落在你写的区间里。**落在区间外不要改区间**，先回头看那一次抽取的条数是不是明显偏少——偏少就是真出了问题，区间不是用来盖住问题的。

**这一步能证明什么，不能证明什么，要说清**：它在同一台机器、同一个 Key、同一个网络下完成，所以它证明不了"换台机器也行"；它能证明的是不依赖你原来的目录、不依赖残留的 `node_modules` 与 `dist`、不依赖手工改过的配置。这个区别要写进交接说明，别写成"我已验证跨机器可复现"。

**做完你应该看到**：另一个目录里 `pytest -q` 全绿，通过条数与原目录相同；页面能打开、两个率有数；B 级做过的话，行数与原目录相同，其余四个在区间内。

### 第 6 步：把"交接"写成 README 里的一节

测试证明"数没变"，文档证明"别人能走到这些数"。两件事都做完，才算能交接。

在 README 里加一节，标题自定（比如「交接须知」），六件事按顺序写：

**一、一分钟版。** 这套系统干什么、有哪几个入口、一条最短的演示路径。写给"只想看它能干什么"的人，不超过十行。

**二、数字口径表。** 第 2 步那张表原样搬进来，含"为什么"那一列。这是整节的核心：它回答"哪些数必须一样"。

**三、从零到有数。** 十步，每步一条命令、标清在哪个目录执行：克隆 → 建环境 → 装依赖 → 配 `.env` → build 前端 → 建库 → 抽取 → 填表 → 起服务 → 跑测试。

这里有一件事必须写进去，否则接手的人一定卡在建库与抽取那两步：**六个数里只有两个率不依赖库。** `a23.db` 与 `.env` 都不进仓库，想看到完整的六个数，中间得补两次动作——跑一次 `import_blocks.py` 把表建出来，再对这份 docx 调一次 `/extract` 把事实抽进去。这一步要多少时间、会不会花钱，也写一句。第 5 步走过的坑，按你实际撞到的顺序写进去。

**四、已知局限。** 至少五条，每条三样：现象、原因、影响。不许写"可能有些小问题"——每条都要指得到具体位置。素材就在前五周里，下面六条任挑五条（想多写也行）：

- 概述段里"上海与北京双双迈上 5 万亿元"这类句子会被抽成伪事实，靠"一行只取本段块号"挡住（第 4 周第 2 步）；
- 判废查三关（块号、原话、`value` 在原话里），但拦不住单位换算——原话"5 万亿元"、`value="5"`、`unit="亿元"`，三关全过，数比真值小了一万倍（第 4 周第 2 步）；
- `/fill` 不会更新两个率，页面上那两个数来自最近一次 `check_fill.py`（第 5 周第 7 步）；
- `dist` 不进仓库，clone 后必须自己 build（第 5 周）；
- 库与 `.env` 不进仓库，新环境必须重建并重抽（第 5 周提交结果第 4 条）；
- 抽取的批大小会影响单批能返回多少条，批太大时表现为"前几段有数、后面整段没有"（第 4 周第 2 步）。

**五、哪些数不能逐位。** 把第 2 步里"区间"那几行单独说一遍，并写明"为什么"与"区间是怎么来的"。这一条最容易被省，但它正是交接时最省时间的部分——接手的人第一个问题通常是"为什么我这数是 498 不是 500"。

**六、出问题先看哪三处。** 三条就够：`dist` 在不在、`.env` 在不在、库里有没有这份文档的事实。这三条覆盖了本周见过的绝大多数"页面没反应"。

写的时候守一条：**每句话都要能被一个没参与过的人验证。** "已充分测试"不可验证；"`pytest -q` 输出 12 passed，其中 5 条比的是 `eval_report.json` 里的数"可验证。

**做完你应该看到**：README 里这一节能独立读通——把前面几节遮住，只看它，能走完全程。写完就提交并 push：第 7 步要对方 clone 你的仓库、只照 README 走；不 push，他拿到的是没有这一节的版本。

### 第 7 步：交叉验收，让别人替你验一遍

自己验自己有个天生的漏洞：你知道每一步该去哪儿，所以你会不自觉地补上文档里缺的那句。这一步就是把这个漏洞堵上。

两两互换 gitee 仓库地址。规则四条：

1. **只照对方的 README 做，不看对方的代码。** 卡住了也不问，先记下来——你问到的答案，下一批接手的人问不到。
2. **从克隆开始，不复用你已有的环境。** 复用等于跳过最容易卡的那一步。
3. **卡住超过 30 分钟就停，记为文档缺陷。** 不是"我不熟"，是他的说明里少了一句。
4. **填同一张表，双向各填一份。** 你验他一份，他验你一份。

表的六项：

| 项 | 填什么 |
| --- | --- |
| 多久起到服务 | 分钟数，起不来就写"未起到" |
| 两个率是否出现 | 六个数里只有两个率不依赖库；其余四个要重建库才有，`/fill` 走不通不算缺陷 |
| 卡在哪一步 | 对应他 README 的第三节第几步 |
| 卡了多久 | 分钟数 |
| 属于什么 | 文档缺一句 / 代码有缺陷 / 环境差异 |
| 一条改进建议 | 具体到"第几步补一句什么" |

收到对方填的表之后，逐条改 README，改完回一句"改了哪几条"。**没改的那几条要写下理由**——有时候是对方环境特殊，有时候是你判断文档已经够了；两种都要留痕，否则下一轮还会撞。

**没有第二个人可以互换时怎么办。** 这一步的目的是"在没有你口头补充的前提下，别人能不能照 README 走完"。有人可换就换；确实找不到，走下面这条替代路径，并如实标注它的局限：

- 表 A（你验对方）、表 B（对方验你）各留一张空表，写明"无可交换对象，未做"，不要编内容；
- 表 C 用"仓库外 clone、只照 README 走"自测：换一个目录、清掉已有环境，从 clone 开始重建，记下分钟数、卡在第几步、属于哪一类。它能验证"README 够不够走通"，验不了"别人读不读得懂"；
- README 与提交说明里写明"交叉验收以单人替代路径完成"，并在已知局限里加一条：缺的是第三方视角，不是缺测试。

替代路径不是"通过"的等价物，它是可核验的降级——比留两张空白表、什么都不做强。

**做完你应该看到**：你手上有两张表，一张是你填的（验对方），一张是对方填的（验你）；走了替代路径的，是表 A、表 B 各一张空表加说明，外加表 C 的仓库外 clone 记录。对方那张表上的"文档缺一句"你都处理过或写了不改的理由。

### 第 8 步：留证，提交

四样证据，缺一样这周就不算闭合：

1. **`pytest -q` 的汇总行**（形如 `12 passed`），抄进 README 或交接说明。
2. **故意改坏那一次的红**：哪一条 failed、期望值、实际值。一行文字就够，不用截图。

提交四样：`backend/test_a23.py`、`backend/requirements.txt`、`README.md`、`.gitignore`（追加的那一行）。还有一份容易漏的：如果你是在第 0 步才生成 `data/eval_report.json` 的，它也要提交——第 3、4 步的断言读的就是它，不提交，别人 clone 下来测试必红。交之前确认两件事：`.env` 与 `data/*.db` 仍在 `.gitignore` 的保护下（`git status` 里看不到它们）；两个新文件没有被挡——`git check-ignore -v` 两条都没有输出才算过，若文件已经 `git add` 过，要加 `--no-index` 再查一次，否则已跟踪的文件即使命中规则也不会显示。

**做完你应该看到**：`git status` 里只有这几样——`backend/test_a23.py`、`backend/requirements.txt`、`README.md`、`.gitignore`（追加 `.pytest_cache/` 那一行）、两张验收表，以及第 0 步才生成的 `data/eval_report.json`（如果确实有变化）；`.pytest_cache/` 与 `eval_report_prev.json` 都不该出现。`git ls-files` 里能看到那两个新文件。

# 第六周任务（第二档 · 挑战档）

第二档不是换一个项目，而是同一条任务的第二层：第一段照第一档完整走一遍，第二段在没有可照抄步骤的前提下，把"我能复现"升级成"别人能判定我复现得对不对"。

两段都做。第一段不是重复劳动——它是第二段唯一的参照物：只有先让那批测试与五个数站稳，你才有依据判断"把判据做成可判定以后，原来那套有没有被改坏"。第二段只给目标、方向提示和验收标准，路径自己规划。选了第二档就按第二档交付：两段都做、都算数。

这一档允许比第一档多两样东西：一份放判据的数据文件，和一条判定用的命令。第一档那句"`test_a23.py` 是本周唯一要写的代码文件"，在第二段不适用——但业务代码仍然一行不改。

## 第一段：第一档本周任务

第一档第 0 步到第 8 步完整走一遍，交付物与通过标准一条不减。走完之后，手上应当有一个全绿的测试文件、一份能重建的环境清单、一节能独立读通的交接说明、两张验收表。第二段从这里开始。

## 第二段：增量任务

### 目标

让"这次一致"从一个只有你能下的结论，变成别人跑一条命令、看一张表就能复核的结论。

第一档结束时，判据在你脑子里、在 README 的一段话里、在几条断言里。三处都在，但它们对不对、够不够，只有你自己知道。这一段要求换一个人来：他不读你的代码，只跑你留的那条命令、只看你留的那张表，就能说出"这次是通过，还是坏了，坏在哪一条"。

对象是 01 那份的六项可判的数——`/parse` 的块数，加行数、写入格数、空着的格数、两个率——与第一段那批测试。第 4 周若按第二档做过 03 那份，它也在范围内：它的分母是三个（应填 17464、应空 330、行数 2542，以你第 4 周的记录为准），形状与 01 不同。做过它的人多出一件收尾活，把三个分母并进同一套口径；这不是本段的难点，是本段最后一步的适配。本周才升档、手上没有 03 的，按 01 单表交付，并在 README 注明"03 不适用"，标准不变。

三条约束，怎么实现都行，但必须守：

1. **第一段的产出不能被改坏。** 第一段那批 `test_` 函数仍全绿，01 的五个数判定结果一条不变（值可以挪位置，不能改大小），页面仍能演示，交接说明仍能独立读通。
2. **同一条判据只在一处定义。** 名称、类型、值或区间，只写在同一个地方；表里写键名与含义，不重复抄数值。两处各写一遍，早晚有一天只改了一处，而你会先信错的那个。
3. **每条判据都能被一条命令判出结论。** 不是"打印一堆数让人看"，是"给出通过或不通过，并且失败时说出是哪一条"。

### 难度在哪里

四件事，没有一件只是"把表做得更细"：

- **判据必须先于结果确定。** 先跑一遍、看一眼数、再把阈值调成刚好包住它——那不是判据，那是给结果写描述。这一条最难守，因为人都会不自觉地"按现在的数调一调"，而且调完自己看不出来。分辨办法只有一个：写下阈值的那一刻，你能不能说"如果实际值超出去，那一定是坏了，不是区间定窄了"。
- **同一个数在两种场景下答案不同。** 同一台机器、同一个库、不重抽时，它必须一位不差；换目录、重建库、重抽之后，它只落在区间里。把这两件事写成一把尺子，必有一种场景天天误报；写成两把尺子而不管它们的关系，第一段那个"改坏就红"的保护就废了——因为区间会替错误放行。这一段最先要解决的，就是这两者的关系。
- **失败信息要能指向判据。** 一条命令跑完只说"失败"，等于把排查工作退还给读输出的人。可用的失败信息是：哪一条、期望什么、实际什么、去哪儿看。这一条不难写，难在你得先站到"只看得到这一屏输出"的位置上想一遍。
- **区间要有推导，不能是拍的。** 一个区间的宽度从哪来？两个数据点之间差多少、差在哪儿、波动与什么相关（抽取条数？批大小？）。只写"±2 应该够"，与"差不多"没有区别，第三个人也没法复算。

还有一句要提前说清：**上面这些全是工程取舍，不是新概念。** 判据表也好、退出码也好、失败信息也好，都用你已有的东西做，不装新库、不加新接口、不改业务代码。三类破坏是把第一档第 4 步那次"改坏"扩大范围，区间推导是把第一档第 2 步那张表再往前推一步——两者都不算新东西，本周的新概念仍然只有回归测试一个。也不接 CI、不为凑区间去重跑抽取刷样本，那两件都超出本周的边界。

### 方向提示

只给方向，不给路径。

- **判据的载体有三种选择：测试代码、单独的数据文件、README 的表。** 三种都能跑，代价不同，选完要能说清为什么。约束里有一条"只在一处定义"——三种载体满足它的方式不一样，先想清楚你要的是哪一种方式，再决定把值与区间放在哪儿。若选数据文件，用标准库就能读的格式，别为它多装一个解析库，那会直接出了技术栈。
- **两种场景怎么共存，是本段唯一必须自己想明白的结构。** 一条命令同时管两件事，还是两条命令各管一件、结论合成一次"通过或不通过"？由你定。判断标准只有一条：同机场景下，一个数从 500 变成 498，必须被判成坏；重建场景下，同一个数落在你写的区间里，必须被判成好。
- **阈值从哪来，决定了它是判据还是描述。** 先定后测，测出来超了就是真有问题；先测后定，你只是在记录现状。两种都会用到，但你得分得清自己用的是哪一种，并在表里标出来。
- **失败时该打印什么，值得单独想一遍。** 把自己放到只看得到这一屏输出的位置上：够不够定位到那条判据、那个接口、那个文件。
- **陌生人的用法要演练一次。** 第一段交叉验收那位就行：只给他命令和表，看他能不能独立得出结论。他若反问"这个区间是什么意思"，说明表还没写完。
- **03 那份若是你的，先想清楚它的三个分母怎么进表。** 它的应填、应空、行数与 01 的"五百格"不是一个形状。同一张表装下两种形状，还是一个表两段，由你定；但"逐位还是区间"的判断标准不能因此变成两套。

### 通过标准

- [ ] 有办法用一条命令（或几条能合成一次结论的命令）判定整体通过与否；通过与不通过的退出码不同，不通过时非零
- [ ] 有一张判据表（就是第一档那张数字口径表扩出来的，不另起一张），每条六项：名称、键名、判据（值或区间）、类型（逐位/区间）、适用场景、失败时看哪里
- [ ] 每条数值判据都能指到断言或验收记录，一一对应、不多不少（一组断言算一条判据；200、404、400 这类行为断言不进表，它们守的不是数）
- [ ] 同一条判据的名称与值只在一处定义：全仓库搜**键名**只命中定义处与引用处。不要靠搜数值判断——同一个数在 `data/`、README、失败样例里天然会重复出现
- [ ] 三类破坏各做一次：改一个数、改一个字段名（第一档第 4 步做过这两种）、删一个文件（本段新增）。每次都要被抓到，且报错说清是哪条判据、或缺哪个文件；破坏前先备份、做完恢复
- [ ] 两种场景各判一次：同机不重抽时，一个数改动一格必须判成坏；重建库时，落在区间内必须判成好。**同机场景下放行区间的做法不算通过**——那会让第一段"改坏就红"的保护归零
- [ ] 每个区间至少两个数据点：第 0 步抄下的那组算一个，本周重建那一次算第二个。两个点可以是同机两次独立重建——它能压住"区间纯属估计"，但证明不了跨机器（第 5 步已写明这个边界）；要跨机证据只能真的换一台机器。只凑到一个点时，这条不勾，写进"已知局限"并说明缺的是哪个点、补它要多久
- [ ] 陌生人判定成立：对方只跑命令、只读表，能说出"通过还是坏了、坏在哪条"，且不需要读代码
- [ ] 第一段那批 `test_` 函数（第一档要求不少于 12 个）仍全绿，五个数判定与第一段一字不差，页面仍能演示
- [ ] 若做过 03：它的三个分母在同一套口径里有位置，判据类型与 01 用同一套说法，没有为它另起一套"逐位还是区间"
- [ ] README 里有三样：判据表、判定用的那条命令、一段真实的失败输出（贴终端里的原文，不要手写"预期效果"）；第一段那张数字口径表与本表合并，它只讲"为什么"，值指向键名；"耗时"与"抽取条数"两行保留为说明行，不计入判据
- [ ] 新增的每一行，你都能讲清它守的是哪一条判据（第 6 周之后没人替你解释）

### 交付物

- 扩展后的判据与判定手段（放在哪儿由你定；判据只有一处，判定是一条命令或几条能合成一次结论的命令）
- README：判据表（六项齐全）、那条命令、真实失败输出、区间的两个数据点
- 若做过 03：一份说明，讲清它的三个分母怎么进同一套口径
- 第一段那批 `test_` 函数与五个数的判定结果一条不变；README 的交接节在原处扩写，不新开一节

### 最低完成线

一条命令能判定整体通过与否；至少六条数值判据（`/parse` 的块数，加 01 那五个数），其中两条在重建场景下也逐位（块数与行数）；三类破坏里至少做完一类，能被抓到并说清是哪条；01 的五个数与第一段那批测试没变；找一个人只读表就能判定通过与否。做过 03 的，把三个分母一并算进来。

做到这一步，这一段就算立住。可以带进比赛材料里补的部分：区间的第二个数据点、失败输出的措辞、03 的适配说明。但有两件不能省：**同一条判据只能住在一处**（住两处，早晚有一天两边不一样，而你会先信错的那个），**两种场景不能混用一把尺子**（混用，要么第一段的保护作废，要么重建永远报错）。

时间紧时的减法顺序（从先到后）：03 的适配不做，只交 01 单表；区间只做两个数（写入格数与一个率），其余先按逐位登记并注明"仅一次实测"；三类破坏只做一类；陌生人判定直接用交叉验收那张表，不另起一遍。**不能减的是第 4 步**（把五个数钉成断言，并改坏验一次）、**第 6 步的"从零到有数"**、以及**第二档的"两种场景各判一次"**——前两个砍掉，本周就没有可交接的东西；最后一个砍掉，判据表就退化成了一张说明文档。

1. 测试红了，先看期望值有没有抄错——本周一半的假红来自"照页面上显示的两位小数抄"。页面显示 `0.94`，`eval_report.json` 里可能是 `0.9432`；断言要拿文件里的完整值。

# 卡住怎么办

**1、一跑测试就报目录不存在，连收集都过不去。**

八成是 `frontend/dist` 没 build。`main.py` 在导入时挂载 `dist`，测试模块顶层导入 `main`，所以缺 `dist` 时整份测试在收集阶段就崩，报错只提目录、不提测试。先在 `frontend/` 里 build 一次再跑。如果 `dist` 明明在还报这个，看两处：挂载是不是写在 `main.py` 末尾（写在前面会把接口一起吞掉）；挂载用的路径是不是从 `__file__` 推出来的（写相对路径时，换个目录启动就找不到）。

**2、测试全绿，但你不确定它到底在不在工作。**

这是本周最要紧的一条。按第 4 步做那两次（改一个数、改一个字段名），看它会不会红——两处是同一个动作，换个对象再做一遍（第二档还会加第三种：删一个文件）。每次都红、报错都指得出是哪一条，它才算在工作；有一次没红，那条断言就是空的。**全绿不是证据，"改坏会红"才是。**

**3、`pytest` 说收集到 0 个测试。**

三个原因，从高频到低频：文件名不以 `test` 开头（pytest 默认只认 `test_*.py` 与 `*_test.py` 两种写法）；函数名不以 `test` 开头；当前目录不是 `backend/`（那样连 `import main` 都会失败，报的是另一条错）。三个都对还是 0，看输出里有没有"collected 0 items"以上的一行警告——它会说清是哪个文件没被收进去。

**4、上传类的断言一直返回 422。**

422 是表单字段名不对。`files` 的键必须是后端那个参数的名字（`/parse` 与 `/extract` 都叫 `file`），值至少两样：文件名、内容。键名写对、值给成单个字符串，也会 422——它要的是"文件名 + 内容"这一对。

**5、新环境装不上依赖。**

先看 `requirements.txt` 里有没有本机路径或指向本机目录的 `-e`；再看 Python 版本是否与原环境差一个大版本；最后确认终端里激活的是新环境，不是系统 Python。三条都排除还失败，就回到原环境重新导出一份清单再试——手工改清单来"修"它，通常越修越远。

**6、新环境页面能打开，点"开始填写"却报库里没有这份文档。**

这不是 bug。`a23.db` 不进仓库，新环境是空的，六个数里只有两个率能出来。想看到完整的六个数，得按 B 级重建库、再抽一次。把这条写进交接说明——接手的人一定会问。

**7、30 分钟没有进展，把四样东西整理好再问。**

"哪一条断言红了、期望值是什么、实际值是什么、我跑的是哪条命令"。这四样凑齐，问题基本一眼能看出来；只贴一句"测试跑不过"，谁也帮不上。这一周的 bug 大多不喊疼——测试没写对的时候，它同样是绿的。
