各路径的职责（每个文件只干一件事）：

| 路径                 | 职责                        | 不该做的事                        |
| ------------------ | ------------------------- | ---------------------------- |
| `config.py`        | 读 `.env`，给出一个 `api_key()` | 不读业务数据，不调模型                  |
| `store.py`         | 建表、写块、写事实、导出              | 不拼提示词，不解析文件                  |
| `extractor.py`     | 拼提示词、调模型、校验与判废、分批、落库      | 不直接写 SQL（走 `store.py`），不处理上传 |
| `import_blocks.py` | 解析样例、写 `blocks` 表         | 不抽事实                         |
| `check_extract.py` | 跑两种模式、导出、打印四行数字           | 不参与接口，不复制抽取逻辑                |
| `main.py`          | 收文件、看后缀、分派、返回             | 不放任何抽取逻辑                     |
| `schema.py`        | 定义形状                      | 不读文件，不连库                     |
| `.env`             | 只放 Key                    | 不放代码，不进仓库                    |
| `data/`            | 放库与导出结果                   | 不放源码                         |

两条约定：

1. **职责不能合并。** 把 SQL 写进 `extractor.py`，第 4 周改表结构时就得通读两个文件；把判废写进 `main.py`，第 5 周接前端时异常会被那个 `try/except` 吞成一句"抽取失败"，连丢弃了几条都看不到。
2. **自测脚本与主代码分开。** `check_extract.py` 只调用、不复制逻辑；它要跟着提交，别人 clone 下来才能算出和你相同的四行数字。

两条位置要求：`.env` 放 `backend/` 下，不要放仓库根——`config.py` 只读当前目录这一份，放错位置会一直报读不到，也不要在两处各放一个；库文件放 `backend/data/`，与 `parse_result.json` 同目录，不要放仓库根，也不要放进 `doc/`。

# 引导和说明：

经过两周的学习，环境、仓库、解析器都已就位；从这周起，我们正式上手真正的软件开发。这一档不会再给你成品代码和成串的命令——只说明每个文件要做什么、怎么确认做对了。拿不准的地方，发动自己的脑筋，去官网和官方文档里找：你要的信息基本都在那儿，只是得自己动手查。

上周结束的时候，我们手上已经有一个能用的入口了：`main.py` 收文件、`schema.py` 定形状、`parser_text.py` 把文字切成块。txt 那份读出 70 块、md 那份 68 块，`backend/data/parse_result.json` 也提交了。

但打开那个 JSON 看一眼就会发现，里面全是没署名的句子。"2024年药品流通行业运行统计分析报告"、"一、发展概况"——它们是什么？是标题还是正文？这一句里有没有一个数？程序一律不知道。它只是把文件切成了行，切得整齐，却一个字也没读懂。

这周要让它开始读。

先别急着动手，把六周摊开看一眼，知道这周站在哪儿：

| 周             | 这周把什么变成什么                    |
| ------------- | ---------------------------- |
| 第 1 周         | 环境与仓库：代码进得去仓库，别人看得懂          |
| 第 2 周         | 文件 → 统一数据：多格式进，一个 schema 出   |
| **第 3 周（本周）** | **文本 → 结构化事实：抽出事实，每条都说得出出处** |
| 第 4 周         | 数据 → 交付物：填进模板，并给出能核对的准确率     |
| 第 5 周         | 后端 → 能用：接上界面，整条链路能演示         |
| 第 6 周         | 能跑 → 能交接：测试、复现、交给别人接手        |

这张表里有件事值得注意：第 2、3、4 周是同一条流水线上的三段，而本周是其中唯一一次"从形式走到内容"。前两周处理的都是形式——文件变成 JSON、几种格式统一成一种；这周处理的才是内容——那句话里到底有没有你要的数。往后两周都长在这周上面：第 4 周填得准不准，取决于这周抽得对不对；第 4 周算不算得出准确率，取决于这周有没有留下出处。

那这周具体干什么？一句话：**把读进来的一段段文字，变成一条条指得回原文的事实。**

可以先想一个下周就会遇到的场景。第 4 周你要往模板里填"某市 GDP"，你打算怎么取？从 70 块里一块块翻，凭眼睛找？还是希望有一个地方明明白白写着"GDP = 17421.4 亿元，出自第 128 块"？后者就是这周要做出来的东西。

所以这周的产出，不是"一堆抽出来的数字"，而是**一条条能自己证明自己的事实**。打个比方：一条事实就是一张卡片，正面写字，背面写它从哪来。

> 正面：南京市 · GDP总量 · 17421.4 亿元  
> 背面：出自《某市统计公报.docx》第 128 块，原话是"全年地区生产总值 17421.40 亿元，比上年增长 4.5%。"

（示意，数字与位置不必当真。）

正面四样（实体、指标、值、单位），背面三样（来源文件、位置、原话），合起来七样。其中**实体和单位允许空着**——有些指标原文就没写主体，有些没写单位，空着比编一个更老实；但**块号、原话、指标名这三样一个都不能空**，它们决定这张卡片还能不能回原文核对。为什么背面不能省？因为第 4 周算准确率时要拿着卡片回原文核对，第 6 周交接时别人要能顺着卡片找回那句话。只有正面的卡片，就是一张谁也不敢用的便条。

那为什么一张卡片只写一个指标，而不是一个城市一张卡、把五个指标并排写上去？可以想三种情况：五个指标通常来自五句不同的话，并成一张卡就得共用一组出处，等于没有出处；同一指标在两年公报里给了两个数，一行一条时两行并排就能看出打架，并成一张卡反而看不出来；第 4 周模板填哪一列就取哪个指标，一行一条，取数就是一句筛选。三个理由指向同一件事——**卡片要能一条一条地被核对**。

这也是这周最需要你动脑子的地方。至于卡片上到底有哪些字段、提示词怎么写、表怎么建，后面的「第一档」会一步步说清，现在不用急着想。

这周还有个新情况：前两周的代码是"确定"的——给同一串字符，切出来的块永远一样，跑一百遍一个结果。这周不一样。"这句话里的 17421.4 是 GDP 还是财政收入"，没有一条规则能把所有写法穷举完，得靠判断。判断交给模型。

所以写法变了：**不是写 `if` 去匹配，而是给它一段原文，再要求它按固定格式回答。** 回答必须是一条条字段齐全的记录；没有，就明确说没有——这句"没有就说没有"一定要写进去，否则它会编一个像样的数字给你。

那要抽什么呢？这里有个容易想岔的地方，先说清楚：**这周抽的不是"字段"，是"事实"。** 字段是模板给的，文档进来的时候还没有模板；但"某个指标 + 一个数 + 一个单位"这种结构，是文字自己带的，不需要谁先告诉你。所以这周做成两种情形：**不给清单时**，让它把每一处"指标 + 数值 + 单位"都抽出来，指标名照抄原文的说法，不改写、不归一；**给了清单时**，只抽清单里点名的指标，其余一律不碰。两种情形共用同一套输出格式、同一张表，差别只在"要什么"这一层。

这周要用大模型，而它有三条脾气，你会反复撞上：同一段话两次调用，措辞可能不同，所以自测比对的是值和条数，不是整段文字；原文没有的指标，它可能顺手补一个，所以每条都要带原话，原话对不上的直接判废；说好返回 JSON，它可能在外面包一句"好的，以下是抽取结果"，所以返回值要用 pydantic 校验，不合格就重试，重试两次还不行就如实报错，别硬塞进库。

这周的工作量大半会花在"怎么问"上。换个说法、加一条约束、给它一个正例，结果能差出一大截。改十几遍是正常的，不是你代码写得差。

还有一件东西得先认识一下：**SQLite**。

前两周存东西靠文件——`parse_result.json` 就是一个文件，写进去、读出来。这周要换个存法。原因很实际：文件只能整个读、整个写，"把 GDP 超过一万亿的城市挑出来"这种事，用文件得先全部读进内存，再自己写循环一条条筛。

SQLite 是一个数据库，但和你听说的那种不一样：**它整个数据库就是一个文件**，不用装服务端、不用起端口、不用账号密码。Python 标准库里已经带了 `sqlite3`，`import` 就能用。

一个库里能放好几张表，表就是行和列，和 Excel 的表格长得一样。差别在**怎么取数**：

```sql
SELECT value_text FROM facts WHERE doc = 'a.txt' AND metric = '营业收入';
```

这一句的意思是"从 facts 表里，取 a.txt 这份文档中指标为营业收入的值"。在 Excel 里，你要点筛选、拖滚动条、用眼睛核对条件；在这里条件写进句子里，程序拿去就能直接用。第 4 周按"实体 + 指标"取数填表、第 5 周前端按文档查，都是这种带条件的取法——所以这周必须换成库，不能继续用文件。

本周够用的只有三句：建表 `CREATE TABLE`、写入 `INSERT`、查询 `SELECT ... WHERE`。第 1 步会说明每句要达成什么，具体怎么写你自己定——不用先去学完 SQL 再动手。

两个坑提前说：写完要 `commit()`，不然关掉程序再打开，看不到刚写的数据；建表用 `CREATE TABLE IF NOT EXISTS`，重复执行不会报错，也就不必每次先删库。

**这周要存的东西分两层。** 一张表存**块**——上周解析出来的那些文字块（`parse_result.json` 里存的就是它），这周入库；一张存**事实**——一行一条，就是刚说的那种卡片。为什么块也要入库？因为卡片背面写的"第 128 块"，得真能在库里按块号查到原话。不存块，想核对一句就得重新解析文件；模板来了要补抽某个字段，也只能从头再跑一遍。至于为什么这周就要落库：后面两周都要回来查——第 4 周按"实体 + 指标"取数填表，第 5 周前端按文档查，第 6 周要复现同样的条数。只把结果放在接口的返回值里，等于每次查看都要重跑一遍模型，又慢又花钱。

**另一样东西得在调用时给，就是清单；可给可不给，也都不写死在代码里。** 程序里不要出现"我要抽 GDP"这种写法：不传清单就通用抽，传了就按清单过滤。这样第 4 周只需要把清单的来源换成模板表头，抽取那一层一行都不用改。它也意味着这周的自测要跑两遍——一遍不给清单，一遍给一份清单，两遍都不改代码。

**这周不做什么。** 记住一句就够：这周只负责"从文字里认事实"，不负责"把事实填进表"。填模板、算准确率是第 4 周的事；做界面是第 5 周的事；多源冲突怎么裁决，是第二档第二段的事，第一档不碰。也不追求把字段抽全——链路通、每条有出处，比多抽二十个指标值钱。如果有人这周就开始写前端、调模板，多半两头都做不实。

**关于两档。** 第一档只做 txt 和 md 两种输入，步骤和命令写全，照着做就能交。第二档两段都做：先照第一档完整走一遍，交付物与标准一条不减，再完成第二段的增量——那一段撤掉步骤，只给目标、方向和验收标准。方向是**多源冲突消解**：同一指标在不同来源给出不同值时，凭什么取这一个、被否掉的值怎么留痕、规则怎么写才能让别人照着走一遍得出同样的结论；四种格式的输入也在那一段铺开。

**怎么算这周做成了？** 不看"我抽出了一堆数"，看三件事。随便挑一条，能说出它出自哪份文件、第几块，并把那句原话对上——这是第一条。同一份文档连跑两遍，条数和值一致，措辞不同没关系，数不能变，模型名和参数要记下来——这是第二条。文档里没有目标指标时返回空而不是编一个，模型返回不合格的 JSON 时程序不崩、还能说清哪一步失败——这是第三条。三条都很朴素，但第 4 周的准确率、第 6 周的复现，全都长在上面。

还有一件事，和上周说的是同一个道理：**这周的活不是"一次写对"，是"改对"。** 上周的障碍是报错看不懂，这周的障碍是模型不按你说的答。两者都不该硬扛：把完整提示词和完整返回一起贴出来，把"我在做什么、它答成了什么、已经试过什么"说清楚，这类问题前人踩得最多，基本问得出答案。第一遍只抽出三成，是正常起点，不必怀疑自己。

最后说时间。这周会第一次有"等模型回话"的时间，进度看起来比上周更慢，这是正常的。

卡过半小时就停下来，把完整提示词和完整返回整理到一起再问，别一个人硬扛。还有一句上周说过、这周更要紧的：可以让 AI 帮你写，但讲不清的代码留不下来——第 6 周交叉验收会指着代码问"这行为什么这么写"，提示词里每一条约束为什么加，你得说得出。

这周的产出会原样成为第 4 周的输入。这周图省事，只存一个值不存原话，第 4 周算准确率时就得回头重抽——那时候的返工，比现在多存两个字段贵得多。

# 第三周任务（第一档 · 引导档）

## 目标

第一档要做成的事只有一件：**文字进库，事实带出处出来。**

具体到可以检查的程度，是三条：

1. 两份样例的块全部入库，块号与原文对得上——txt 那份 70 块、md 那份 68 块。
2. 不给清单也能抽出事实，每条都带块号和原话；原话必须能在库里那一块查到。
3. 给清单时只抽清单内的指标；同一份文档连跑两遍，条数不翻倍。

## 任务清单

先把路线说清楚：

装依赖与 Key → 建库建表 → 块入库 → 写抽取器 → 接接口 → 自测留证。

每一步末尾都有"做完你应该看到"。这一档不再给成品代码，只给**每个文件要做什么、输入输出是什么、怎么验证**；代码要你自己写，写不出来时按"做完你应该看到"一条条对。

### 第 0 步：进环境，装依赖，配好 Key

四件事，按顺序做：回到仓库根目录 → 激活环境 → 进 `backend/` 装包 → 把 Key 写进 `.env`。

**第一步：把终端切到仓库根目录。**

切到第一周建的那个仓库根目录，不是 `backend/`。环境建在仓库根下，在别处激活会找不到。

**第二步：激活你第一周建的那个环境。**

用你第一周建它时的那套方式激活，不用换。判断标准只有一个：命令行提示符最前面出现了环境名，比如 `(.venv)` 或 `(a23)`。看不到就是没激活，别急着往下走。

**第三步：进 `backend/`，装两个包。**

要装的是 **`httpx`** 与 **`python-dotenv`**。这两个都在第 2 周 `fastapi[standard]` 的依赖链里，多数人已经装好；`import` 不通时再单独装。具体的下载命令不再给出，需要你自己去官网上找。

两个包各自的用途：

- `httpx`：调 DeepSeek 接口用的 HTTP 客户端。第 2 周如果装过 `fastapi[standard]`，它通常已经被一起带进来了，安装时只会提示需求已满足——那不是失败。
- `python-dotenv`：读 `.env` 用的，负责把文件里的键值对塞进环境变量。它通常随 `uvicorn[standard]` 一并装入，`import dotenv` 不通时再单独装。

装完确认三个模块都能导入：`httpx`、`dotenv`、`sqlite3`。

**做完你应该看到**：三个模块导入都不报 `ModuleNotFoundError`。没有输出就是好结果，报错才要看。

这里有个常犯的错：导入名是 `dotenv`，不是 `python-dotenv`。安装时用带前缀的名字，导入时不用；写错会以为包没装，其实早就装好了。

**第四步：把 Key 写进 `.env` 文件。**

这一步不做，后面调模型时会报"没有读到 DEEPSEEK_API_KEY"。Key 从哪来、写到哪、怎么保证它不被提交，三件事按顺序做。

**一、去官网拿 Key。**

1. 浏览器打开 `platform.deepseek.com`，用手机号或邮箱登录，没有账号先注册。
2. 登录后进「API keys」，点「创建 API key」，名字随便填，比如 `a23`。
3. 弹窗里那串 `sk-` 开头的字符就是 Key。**它只完整显示这一次**，当场复制：关掉弹窗就再也看不到，只能删掉重建一把。

**这个 Key 一个字都不能泄露给别人。** 它等同你的支付凭证：谁拿到，谁就能用你的账号调模型，产生的费用记在你名下，你既拦不住也退不回。所以不管什么理由——同学借去试一下、群里有人问你怎么配、交作业要附配置截图——都不要把 Key 发出去。截图也不行，露一半也不行；贴进聊天窗口、写进作业文档、存进网盘同样算泄露。

反过来也一样：不要用别人的 Key。每个人用自己注册的那把，出了问题才查得清是谁的额度、哪一次调用。

顺手看一眼充值或用量页面。新账号通常有赠送额度，余额为 0 时调用会返回 `402`，那是没钱，不是代码写错了。

**二、先改 `.gitignore`，再建文件。**

顺序不能反。`.env` 里是明文 Key，它一旦进了 git 历史，事后把文件删掉也没用——旧提交里仍然留着，只能去后台把 Key 删掉重建。所以先把门关上，再往里放东西。

打开仓库**根目录**的 `.gitignore`，在末尾追加一条忽略规则，内容就是 `.env` 这个名字。写在根目录这一份里，任意子目录下的 `.env` 都会被一起挡住，不必写成 `backend/.env`。

库文件同样要挡住，规则是 `data/*.db`——这一行可以等第 1 步建完库再补，但提交前必须有两行：`.env` 和 `data/*.db`。

保存后，`git status` 里就再也不会出现这两类东西。

**三、在 `backend/` 下建 `.env`。**

在 `backend/` 里新建文件，文件名就叫 `.env`——前面一个点，后面没有后缀。

**注意**：用记事本的同学，默认会把文件存成 `.env.txt`，而扩展名被系统藏起来，你看到的仍是 `.env`，以为成功了，实际没生效。要么用 VS Code 建，要么先在资源管理器里打开"显示文件扩展名"再改名。

文件里只写一行，长这样：

```

```

拆开看就是两个部分：**等号左边是键名**，固定写 `DEEPSEEK_API_KEY`，一个字都不能改，程序就是照这个名字去取的；**等号右边是值**，换成你刚才复制的那串 `sk-` 开头的 Key。整行只有这一条，没有标题、没有引号、没有分号。

三个细节：等号两边不要空格——一旦写成 `DEEPSEEK_API_KEY = sk-xxx` 这样，程序读到的是空值，而且不报错，这种错最难查；Key 不要加引号；这一行后面不要写中文注释。

**四、写 `config.py`，让程序读得到它。**

`.env` 不会自己变成环境变量，得有代码去读。新建 `backend/config.py`，它只干一件事：对外提供一个函数，调用它就能拿到那串 Key；读不到时抛一句能看懂的错。下文按 `api_key()` 称呼它，名字你可以改。

用 `python-dotenv` 的 `load_dotenv()` 完成读取，它会把 `.env` 的每一行塞进 `os.environ`。这个函数还有几个可选参数（比如指定文件路径、指定编码、是否覆盖已有的环境变量），名字以官方文档为准。

写的时候守住四条，缺一条都会在别处变成难查的错：

1. **先加载，再取值。** `api_key()` 被调用时才读也行，模块导入时读一次也行，但取值前必须已经加载过。
2. **编码用 `utf-8-sig`。** 记事本存出来的 `.env` 带 BOM，用默认编码读，第一行的变量名会多出一个看不见的字符，表现是"文件里明明写了，程序却读不到"。
3. **读不到要自己抛错。** `load_dotenv()` 在文件不存在时**不报错**，只是什么都没读进来。所以取值后要判断空串，抛一句中文提示，指明"确认 `backend/.env` 存在且命令行在 `backend/` 下"。不写这句，错误会推迟到调模型时才暴露，提示和配置八竿子打不着。
4. **不要覆盖已存在的环境变量。** 机器上真设过的值应当优先，`.env` 只作兜底。`load_dotenv()` 默认就是这个行为，别去改。

验证方式：在 `backend/` 下写一行调用 `api_key()`，打印返回值的长度。

**做完你应该看到**：打印出一个大于 0 的数字（Key 通常三十多位）。它打印的是长度而不是 Key 本身，可以放心截图。

报"没有读到 DEEPSEEK_API_KEY"，八成是三个原因：文件建在了仓库根目录而不是 `backend/`；文件名实际是 `.env.txt`；当前命令行不在 `backend/` 目录下。

三条纪律，从这周开始真正用 Key，务必守住：`.env` 必须在 `.gitignore` 里，并且在你写 Key 之前就加好；`.env` 不发给任何人、不贴进聊天窗口截图；一旦发现它已经被提交上去，立刻去后台删除这把 Key 并重建，别只改代码。


### 第 1 步：建库，把两张表建出来

先说一句：从这一周开始，我们不会再给任何成品的代码，需要大家根据提示自己写出来。

新建 `backend/store.py`。它只跟库打交道：建表、写块、写事实、导出；不调模型，不解析文件。

**先想清楚要存什么。** 两张表，列名、类型和约束都在下面。这就是你要写出来的建表语句——具体怎么写、SQL 怎么用、Python 怎么调 SQLite，需要大家自己去查。

`blocks` 表：一行一块，是文档的原样。

| 列            | 类型      | 约束                        | 说明                       |
| ------------ | ------- | ------------------------- | ------------------------ |
| `id`         | INTEGER | PRIMARY KEY AUTOINCREMENT | 自增主键，不用自己给               |
| `doc`        | TEXT    | NOT NULL                  | 文件名，带后缀                  |
| `block_no`   | INTEGER | NOT NULL                  | 块在原文里的行号                 |
| `block_type` | TEXT    | NOT NULL                  | 块类型，第 2 周统一是 `text_line` |
| `text`       | TEXT    | NOT NULL                  | 块的内容                     |

另外两条约束：`doc` 与 `block_no` 的组合必须唯一（`UNIQUE (doc, block_no)`）；表名就叫 `blocks`。

`facts` 表：一行一条事实。

| 列            | 类型      | 约束                        | 说明                        |
| ------------ | ------- | ------------------------- | ------------------------- |
| `id`         | INTEGER | PRIMARY KEY AUTOINCREMENT | 自增主键                      |
| `doc`        | TEXT    | NOT NULL                  | 来源文件，与 `blocks.doc` 对得上   |
| `block_no`   | INTEGER | NOT NULL                  | 指向 `blocks.block_no`      |
| `entity`     | TEXT    | 可空                        | 主体，如"南京市"；抽不出就空           |
| `metric`     | TEXT    | NOT NULL                  | 指标名，照抄原文说法                |
| `value_text` | TEXT    | NOT NULL                  | 原文写法，如 `1,234.5`、`13.7万亿` |
| `value_num`  | REAL    | 可空                        | 清洗后的数字；清不出就存 NULL，不要瞎猜    |
| `unit`       | TEXT    | 可空                        | 单位，如`亿元`；原文没写就空           |
| `snippet`    | TEXT    | NOT NULL                  | 能证明这条事实的原话                |
| `mode`       | TEXT    | NOT NULL                  | 抽取模式：`general` 或 `list`   |

还要在 `facts` 上建一个索引，覆盖 `doc` 与 `metric` 两列——第 4 周填表时最常见的条件就是"哪份文档、哪个指标"，让它先落在索引上。要按实体筛，就再加一列。

**为什么要两张表。** `blocks` 是原文，`facts` 是结论。事实里记的"第 128 块"，靠 `doc + block_no` 到 `blocks` 里查原话；不存块，这句话就无处可查。为什么 `blocks` 上要有那个唯一约束：同一份文档跑几遍，块不该越堆越多，重复写入要被替换而不是追加。为什么 `facts` 要有 `mode` 列（`general` / `list`）：两种模式的结果要能分开看，混在一起，第 5 步的自测就没法比对。

**再写五个函数。** 名字可以自己定，但职责必须分得这么清：

| 函数                               | 输入             | 返回      | 必须做到                                         |
| -------------------------------- | -------------- | ------- | -------------------------------------------- |
| `connect()`                      | 无              | 一个数据库连接 | `data/` 目录不存在时先创建；库文件路径是 `data/a23.db`       |
| `init_db()`                      | 无              | 无       | 建两张表与索引；**重复执行不报错**；写完要提交                    |
| `save_blocks(doc, blocks)`       | 文件名、`Block` 列表 | 写入条数    | 同一 `doc` 同一 `block_no` 覆盖而非追加；块号取自 `locator` |
| `replace_facts(doc, mode, rows)` | 文件名、模式、七元组列表   | 条数      | **先删**同 `doc + mode` 的旧记录，再插；写完提交            |
| `dump_facts(path)`               | 导出路径           | 条数      | 全表按 `doc`、`block_no` 排序写成 JSON；中文不转义，缩进 2    |

下文按上面这张表的名字称呼这几个函数，你改过名对应着看即可，不必为了对齐再改回去。

写 `init_db()` 时我们就需要用python调用SQL语句。这周只用四个动作：

| 语句             | 干什么         |
| -------------- | ----------- |
| `CREATE TABLE` | 建一张表，声明有哪些列 |
| `INSERT`       | 往表里写一行      |
| `SELECT`       | 按条件取数据      |
| `DELETE`       | 按条件删数据      |

语法长这样，一行一个字段，"字段名 + 类型 + 约束"：

```sql
CREATE TABLE 示例 (
    id INTEGER PRIMARY KEY,
    name TEXT NOT NULL
);
```

三条书写习惯：语句用分号结尾；关键字大写只是习惯，SQLite 不区分大小写；文本值用单引号（`'a.txt'`），别用双引号——SQL 里双引号表示"列名"，写错了报错信息很难懂。

还有一处容易看岔：往 SQL 里传值时，用 `?` 占位，真正的值按顺序从第二个参数传进去，别用字符串拼接。好处有两个：引号和换行不用自己转义；也不会因为把外部内容拼进 SQL 而出问题。

**如果你第 2 周改过字段名，这一段必须跟着改。** 第 2 周说过那几个名字是推荐写法、不是规定，有人可能把 `file` 写成了 `doc_name`、把 `text` 写成了 `content`。照抄别人的建表语句，程序跑起来会报 `KeyError` 或 `AttributeError`——不是 SQL 写错了，是名字对不上。对照你自己的 `schema.py` 核这四处：

| 表里的列         | 对应你 `schema.py` 里的什么                   |
| ------------ | -------------------------------------- |
| `doc`        | `ParsedDoc` 里存文件名的那一个字段（第 2 周叫 `file`） |
| `block_type` | `Block.type`                           |
| `text`       | `Block.text`                           |
| `block_no`   | `Block.locator` 里的键，txt 与 md 都是 `line` |

第 2 步的 `save_blocks` 和 3.3 的判废用的是同一套名字，要一起改——否则建表这一步过了，后面还会连着错两次，而且报的是 `KeyError: 'line'` 这类看不出根因的错。

表名（`blocks`、`facts`）建议不要动：后面每条 SQL 都写着它们，改名就得全文替换，而收益是零。

**做完你应该看到**：运行一次建表函数不报错；再查一下库里有哪些对象，里面应当有 `blocks`、`facts` 两张表，以及你在 `facts` 上建的那个索引。查法随你——自己写两行打印出来，或用能打开 SQLite 文件的工具看一眼，都行。

### 第 3 步：写抽取器

新建 `backend/extractor.py`。这一步分五小段，一段跑通再走下一段，别一次写完再调。

这个文件是一条小流水线，从头到尾七件事，各写一个函数，名字自定：

| 要做的事 | 拿什么 | 交出什么 |
| --- | --- | --- |
| 拼提示词 | 文件名、这一批块、可选的清单 | 一段提示词文本 |
| 调模型一次 | 提示词 | 解析后的字典 |
| 调模型并校验，不合格重试 | 文件名、这一批块、清单 | 能取到事实列表的对象 |
| 判废：块号真、原话对、`value` 在原话里 | 事实列表、这一批块 | 通过的事实列表 |
| 把原文字符串清洗成数字 | 一个字符串 | 小数，或 None |

| 主流程 | 解析结果、清单 | 含条数与模式的字典 |

最后一行是主流程，它把前六件串起来：切批 → 逐批调用 → 汇总 → 整批落库 → 返回。

`Block`、`ParsedDoc` 都从 `schema.py` 导入；`httpx` 第 0 步已装好。

**3.1 先让一次调用跑通。**

用 `httpx` 向 DeepSeek 发一个 POST。请求要素就这些，一个都不能少：

| 项                     | 值                                                           |
| --------------------- | ----------------------------------------------------------- |

| 方法                    | POST                                                        |
| 请求头                   | `Authorization: Bearer <你的 Key>`；内容类型由 `httpx` 传 JSON 时自动带上 |

返回的 JSON 里，答案在 `choices[0].message.content`，是一个**字符串**，要再解析一次。三件事别省：`raise_for_status()` 要有，Key 错、余额不足、模型名写错都靠它抛出来，否则你只会拿到一个空结果发呆；超时要设，不然卡住时界面像死了一样；解析失败要能被捕获，模型有时会在 JSON 外面裹一句话。

**做完你应该看到**：能看到键 `ok` 的值是真——打印成 `{'ok': True}` 还是 `{"ok": true}` 都算对，取决于你打印的是解析后的对象还是原始字符串。这一步不通，后面全是白写。

**3.2 把提示词写对。**

提示词是这周唯一需要反复改的东西。骨架如下，方括号里是要你填的部分：

```
文档：[文件名]
[抽取范围]

规则：
1. 只抽原文写出的数字，不计算、不推断。
2. 指标名照抄原文说法，不改写、不缩写。
3. 数值与单位照抄原文；原文没写单位就留空。
4. 每条给出块号，并抄一段能证明它的原话。
5. 找不到就返回空数组，不要编造。

原文：
【块号 1】……
【块号 2】……

只输出 JSON，形状如：{"facts":[{"block_no":33,"entity":"","metric":"","value":"","unit":"","snippet":""}]}
```

`[抽取范围]` 一句话，两种模式只差这里：不给清单时写"抽取文中出现的每一个「指标 + 数值 + 单位」"；给了清单时写"只抽这些指标：A、B、C；其他一律不抽"。别为两种模式写两套提示词。

原文要带上块号再送进去（`【块号 33】` 这种写法），否则模型无从给位置。三条规则最容易被省、也最要紧："指标名照抄不改写"不写，它会把"地区生产总值"改成"GDP"，改完你连它抽的是哪个指标都判断不了；"找不到就返回空"不写，它会补一个看起来合理的数；"每条给出原话"不写，3.3 就没法判废。

**3.3 校验与判废。**

模型返回的东西不能直接信。先按这个形状校验，字段缺了或类型不对就重试——用第 2 周那个 `BaseModel` 建一个模型来做最省事，校验不过它会直接抛 `ValidationError`：

| 字段         | 类型  | 必填      |
| ---------- | --- | ------- |
| `block_no` | 整数  | 是       |
| `entity`   | 字符串 | 否，没有就空串 |
| `metric`   | 字符串 | 是       |
| `value`    | 字符串 | 是       |
| `unit`     | 字符串 | 否       |
| `snippet`  | 字符串 | 是       |

再把这一批的结果过三道关，过不了就丢：

1. **块号必须真在这一批里。** 模型可能给一个不存在的块号，或者给上一批的块号。
2. **原话必须是那一块里的连续片段。** 去掉空格后做包含判断即可；模型常常把换行和多余空格改掉，但不该改字。
3. **`value` 必须能在这段原话里找到。** 把两边的空格、千分位逗号去掉，`value` 应当还是 `snippet` 的子串。`value="50000"`、原话是"迈上 5 万亿元"这种，数字与原话对不上，说明模型自己换了算——填进模板就是错数，这一关必须拦。

这三条是这周最值钱的判断：**块号真、原话对、数字在原话里，才叫可溯源。** 任何一条不满足，这条事实就是模型编的或算错了，一律丢。

数字由程序算，不要让模型再给一个：拿 `value` 字符串，去掉千分位逗号与空格，尝试转成小数，转不成存 NULL。带"万""万亿"这类量级的写法（比如 `13.7万亿`）会得到 NULL——这是故意的，本周只保证原文不丢，换算成统一单位是第 4 周的事。

**3.4 分批送。**

一份文档几十到上千块，不能一次全塞给模型，也不能一块一块送。按固定大小分批，每批若干块、带上各自的块号一起送。

批大小的起点取 30。批太小，一份文档要调用几十次，慢；批太大，模型开始把位置张冠李戴。跑完第一份，看看"丢弃了几条、为什么丢"再调。

主流程是三步循环：切批 → 每批调用并校验判废 → 汇总后整批落库。落库只做一次，别每批写一次——中途失败会留下半截数据。

**3.5 落库。**

把通过判废的事实转成七元组，顺序与你表里的列对齐：块号、主体、指标、原文值、清洗后的数、单位、原话。然后交给 `replace_facts`，连同文件名与模式一起传进去。

它先删同 `doc + mode` 的旧记录再插，这就是"跑两遍条数不翻倍"的做法。别直接追加——第一次跑完挺好，第二次跑完数据翻倍，到第 4 周算准确率时才发现分母不对。

**做完你应该看到**：对 txt 那份跑一次，`facts` 表里多出若干条；`metric` 里是原文说法，像"营业收入""销售总额"这类，不是被改写成简称的样子；`block_no` 都落在 1–70 之间。条数多少不用跟别人比，它取决于你的提示词。

### 第 4 步：接到接口上

`main.py` 里**加**一个路由，不要删掉第 2 周的 `/parse`——它还得用。这个文件里已经有 `app = FastAPI()`，不要再写第二遍：再写一遍会建出第二个 app，`/parse` 挂在前一个上，等于被静默丢掉了。

接口规格：

| 项              | 值                                                                          |
| -------------- | -------------------------------------------------------------------------- |
| 路径与方法          | `POST /extract`                                                            |
| 表单字段 `file`    | 必填，上传的 txt 或 md                                                            |
| 表单字段 `metrics` | 可选，逗号分隔的指标名；留空即通用模式                                                        |
| 成功返回           | `{"doc": 文件名, "mode": "general" 或 "list", "count": 抽出条数, "kept": 通过判废的条数}` |

处理顺序四步：读文件内容与文件名 → 看后缀，只接 `txt` 与 `md`，其余返回 400 并说明是什么类型 → 把 `metrics` 按逗号切开、去掉空项，切完是空就当作"没给清单"（走通用模式）→ 整段处理包在 `try` 里，任何异常都翻成 400 加一句中文原因。

错误码只有两种，别混：

| 情况                       | 返回  | 提示内容        |
| ------------------------ | --- | ----------- |
| 后缀不支持                    | 400 | 说明是哪种格式，未支持 |
| 抽取过程出错（超时、非 JSON、没有 Key） | 400 | 说明失败原因      |

## 第二段：增量任务

### 目标

让抽取覆盖四种格式的输入——txt、md、docx、xlsx。

再让"同一指标在不同文档里给出不同值"这件事在库里说得清、复核得了：既不静默覆盖，也不把不同期次当成冲突。

两条约束，怎么实现都行，但必须守：

1. **第一段的产出不能被改坏。** txt 仍是 70 块、md 仍是 68 块；`/extract` 的返回结构不变；判废那三关不能省。
2. **格式清单只维护一处。** 支持哪些后缀、每种怎么解析、各自产出什么块，写在一处；不许为某一种格式另起字段，也不许另开接口。

纳入抽取链路的两份输入仍取 `doc/02_输入样本/` 里第 2 周那两份：docx 用 `05_南京市国民经济和社会发展统计公报_2021-2024.docx`，xlsx 用 `05_COVID-19全球数据集_节选.xlsx`。同一批文件，数字才有可比性；换一份，下面那些参照值就都不作数了。

### 难度在哪里

四件事，没有一件只是"多写两个解析器"：

- **四类输入的"块"不是同一种东西。** docx 的块是段落和表格单元格，xlsx 的块是数据行，txt 与 md 的块是行。"第 3 块"在四种文件里指的不是同一种位置，所以 `block_no` 只管"文档内第几块"，结构化位置（第几张表、第几行、第几列）要另外留住处——第 4 周填表出错时，全靠它定位到那一格。
- **xlsx 不是"再读一个文件"，是换一种规模。** 最大那份 `max_row` 是 38473 行、15 列（`A` 到 `O`）——38473 是按"存在过的单元格"算出来的行号上限，含大量带格式的空行，真正有值的约一万五千行。全量送模型既慢又贵，也不必要。范围怎么划——哪张工作表、多少行、按什么条件截——是这层真正要做的判断：划窄了漏数据，划宽了跑不完。
- **"冲突"多数是假冲突。** 同一指标在不同文档里数值不同，绝大多数不是矛盾，是期次不同、范围不同、说法不同。得先分清"是不是同一个格子"，才轮得到"取哪个"。顺序反了，就会写出一堆处理 2023 与 2024 差值的规则，方向从一开始就错。
- **验收比实现难。** 抽取条数变多不等于变好。能说清"四类各多少条、可溯源多少、同一指标有几处多值、每处怎么定的"，才算做完。

### 方向提示

只给方向，不给路径。

四类输入的结构差异，先看清再动手：

| 格式 | 原文里有什么 | 块大概是什么 | 最容易漏的地方 |
| --- | --- | --- | --- |
| txt | 一个个段落 | 一行一块，空行跳过 | 第一段已做过，别动 |
| md | 标题、段落、列表 | 一行一块，空行跳过 | 同上 |
| docx | 段落与表格是两组对象 | 段落一块，表格单元格各一块 | 表格里的数最值钱，只读段落会整类漏掉 |
| xlsx | 工作表、表头、数据行 | 一行一块，表头不单独成块 | 表头决定每列是什么指标，丢了表头，行里的数就没有含义 |

- **docx**：解析第 2 周已经做过，直接复用，本周只做入库与抽取。段落与表格的先后顺序保不保，是个取舍，写进 README。自查锚点：这份文档的 18 张表是两套同构表，两半各 473 个单元格、合计 946；只读一半会得到 473。
- **xlsx**：范围由你定，但要在 README 说明"为什么划在这里、漏掉了什么"。这份数据划到哪里都是取舍，说得出理由比划得宽更重要。参考量级：200 行上下就够本周用——一万五千多行全量送模型要五百多次调用，既跑不完也不必要；具体取多少、分几批，按你的调用预算定，写进 README。
- **表头怎么留**：数据行的块文本建议写成"列名: 值｜列名: 值"这种带列名的形式，让每一行自己说得清哪个数是什么。表头不单独成块，但表头信息不能丢——否则判废时模型给出的原话在裸数字的行里找不到，整条会被丢掉。
- **指标名的归并**："地区生产总值 / GDP / 生产总值"要能对上同一个键，但原文说法不能丢。归并放在落库层做，`metric` 列照旧抄原文，提示词规则不动——"照抄不改写"是判废的前提，别为了归并把它改掉。加一列还是另建映射表，由你定。
- **期次与实体**：从块的文字里取，别用文件名猜。同一份公报常含好几年数据，期次取错，后面全错。一块里出现多个年份时，按这个顺序定：先取与该数值同一句的那个年份；同句还有多个，取其中最大的；整块都判不出来，才继承上文的年份标题块。三种情况都要在 README 写一句"我按哪条定的"。期次要有个落脚的地方——加一列，或并进归并键；只留在原话里，第 4 周二档按日期区间筛就没法做。跨批时允许从同文档最近的年份标题块继承，继承规则写进 README。
- **多值留痕**：同一"实体 + 指标 + 期次"出现多条时，不要后写覆盖前写，留多条候选，另记"采用了哪条、依据是什么"。这里的"不覆盖"只指同一次抽取内同键多条都要保留；跨运行的幂等仍按 `doc + mode` 先删再插，否则第二遍会翻倍。
- **自测**：第一段那个自测脚本扩成四份文件，口径见下面通过标准第 10 条；xlsx 的条数按你划定的范围算。

- `backend/data/` 下四个文件：`facts_export_txt.json`、`facts_export_md.json`、`facts_export_docx.json` 全量；`facts_export_xlsx.json` 按 README 范围导出，超过 200 条时取前 200 条，并注明"范围内共 N 条，导出 200 条"——八行表里 xlsx 那一行填的是范围内全量抽出条数，以表为准，导出只是截取。第一档那个 `facts_export.json` 保留不动
- README：四种格式支持清单、八行数字表、xlsx 范围与理由、三句话口径、每个新增函数一行说明

### 最低完成线

四类输入各返回 200，且各至少抽出 1 条通过判废的事实（xlsx 按你划定的范围）；txt 与 md 的块数没被改坏；docx 块数落在区间内（表格没整类漏）；同键多值不静默覆盖，依据可查——这条增量就算立住。

xlsx 可以先只跑一张工作表；同义词表可以先只覆盖 3 个（地区生产总值 / GDP / 生产总值）；期次可以先只覆盖"块里写着年份"的那些；除 txt 外的三份可以先各跑一遍。但有两件不能省：**表头信息不能丢**，丢了 xlsx 的数就没有含义；**多值不能覆盖**，覆盖了第 4 周就只能看到一个数，取错了也查不出来。

# 卡住怎么办

**1、抽出条数是 0，或远少于预期。**

先分辨是"原文真没有"还是"判废把对的也丢了"。把丢弃原因打出来：块号不在批内 → 分批时块号没带对；原话找不到 → 提示词让它改写了；`value` 不在原话里 → 模型自己换了算。三种原因的改法完全不同。

**2、同一条事实跑两遍变多或变少。**

变多，多半是落库没先删同 `doc + mode` 的旧记录；变少或忽多忽少，先把 `temperature` 固定为 0、批大小固定住再看，别急着改提示词。

**3、`snippet` 引用的块号对不上原文。**

`block_no` 是"文档内第几块"，不是行号。docx 的块里既有段落也有单元格，行号与块号只在 txt 里恰好相等。回 `blocks` 表按 `block_no` 取文本核对，不要拿行号去原文里数。

**4、xlsx 抽出来的数没有含义。**

表头信息丢了。数据行的块文本要写成"列名: 值"的形式，让每一行自己说得清哪个数是什么；表头不单独成块，但列名必须随行进块文本。

**5、同一指标在库里查不到，或查出好几条。**

查不到，先看 `metric` 是否照抄了原文说法——归并只应发生在查询层，不该改写 `metric` 列。查出好几条，是期次或口径不同，属正常多值，按"采用了哪条"的记录去判断，不要用后写覆盖前写。

**6、`ModuleNotFoundError` 又出现了。**

先看提示符前有没有环境名。这周要用的 `httpx`、`dotenv` 若提示找不到，先 `import` 试一次再决定要不要装——它们多半已在第 2 周的依赖里。

**7、30 分钟没有进展，就把三句话整理好再问。**

"我在做什么、我看到什么（包括那个不对的数或那条被丢的记录）、我已经试过什么"。这一周的 bug 大多不报错，只有数字不对，所以"我看到什么"里一定要带具体的块号和原话。
