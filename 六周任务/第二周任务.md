```
a23-project/
├── backend/
│   ├── main.py                 # FastAPI 入口：接一个文件、按后缀分派、返回统一结构
│   ├── schema.py               # 统一数据模型：只此一份，解析器按它输出
│   ├── parser_text.py          # .txt / .md → 统一结构
│   └── data/
│       └── parse_result.json   # 调用接口拿到的解析结果（要提交）
├── doc/                        # 本周发放，放进仓库根目录（与 backend/ 同级）
│   └── 02_输入样本/             # 这周测试用的文件都在这儿
├── frontend/                   # 本周不动
├── README.md                   # 追加：怎么跑、跑出什么数
└── .gitignore                  # 第一周已建；本周末尾加一行 check.py
```

各路径的职责（每个文件只干一件事）：

| 路径               | 职责                        | 不该做的事      |
| ---------------- | ------------------------- | ---------- |
| `main.py`        | 收文件、按后缀分派、把结果序列化返回        | 不写任何解析逻辑   |
| `schema.py`      | 定义字段、类型、必填与否              | 不读文件、不做解析  |
| `parser_text.py` | 把 txt / md 读成 `ParsedDoc` | 不许私自加字段    |
| `data/`          | 存放调用接口得到的解析结果             | 不写代码、不参与解析 |

两条约定：

1. **文件名可以改，职责不能合并。**把三种格式的解析全塞进 `main.py`，第 3 周改一处就得通读全文。
2. **测试输入就用发下来的那一份。**这周发的 `doc/02_输入样本/` 是全部输入，放进仓库后直接用它们跑，不要改名、不要增删、不要另建一套；换了文件，数字就跟别人的不可比。要提交的是 `data/` 下那份输出 JSON——别人复现你的数字，靠的就是它。

两条位置要求：`main.py` 在 `backend/` 里，安装与启动命令都在 `backend/` 目录下执行；程序所在路径保持英文、无空格（第一周已说过）。样例文件是中文名，保持原样即可——你的程序本来就要能处理这种文件名。

# 引导和说明：

上一周结束的时候，我们的仓库其实还是空的：README 里记了四条版本号，backend/ 和 frontend/ 里各躺着一个 .gitkeep。但地基是实的——环境能跑、代码能提交、gitee 上能看到你做了什么。这周开始，仓库里要真长出东西了。

先别急着动手，把六周摊开看一眼，知道这周站在哪儿：

| 周             | 这周把什么变成什么                          |
| ------------- | ---------------------------------- |
| 第 1 周         | 环境与仓库：代码进得去仓库，别人看得懂                |
| **第 2 周（本周）** | **文本文件 → 统一数据：txt、md 进来，出去是同一种结构** |
| 第 3 周         | 文本 → 事实：从结构里抽出字段，每条都说得出出处          |
| 第 4 周         | 数据 → 交付物：填进模板，并给出能核对的准确率           |
| 第 5 周         | 后端 → 能用：接上界面，整条链路能演示               |
| 第 6 周         | 能跑 → 能交接：测试、复现、交给别人接手              |

看完这张表，有件事值得注意：第 2、3、4 周不是三件互不相干的事，而是一条流水线上的三段——这周把文件读进来，下周从里面认字段，第 4 周把字段填进模板。流水线断在哪一段，后面都接不上。这周做的，是流水线的入口。

那这周具体干什么？一句话：**把我们手上这堆格式不一样的文件，读成同一种结构。**

为什么要"同一种"？可以先想一个下周就会遇到的场景：周一拿到的是 txt，周二拿到的是 md，如果两种文件读出来的数据长得完全不一样，那你下周每写一个字段都得写两遍适配；等到第 4 周往模板里填，还得再写一遍。反过来，如果这周就把两种格式压成同一个样子，下周面对的只有一样东西。

所以这周真正的产出，不是"几个能读文件的函数"，而是**一份所有格式都必须服从的数据结构**。打个比方：两个人交简历，一个写成纯文本，一个用 Markdown 排版，HR 不需要会两种写法，她只要一张固定格式的登记表——姓名、电话、经历。各写各的，登记表只有一张。这张登记表，就是这周要做出来的东西。

这也是这周唯一需要你动脑子设计的地方。至于每种格式具体怎么读、结构里放哪些字段、代码怎么写，都在后面的「第一档」里一步步给，现在不用急着想。

这周还有个新情况：你会第一次把写好的 Python 代码变成一个能通过网址调用的接口。听着像新东西，其实只是换了个入口——上周你在终端里跑脚本，这周在浏览器里点一下、看它返回结果。真正要花时间的是那份数据结构和两种格式的读法，接口只是把它们串起来的那根线。

先把两个词说清楚，这周你会反复碰到它们。

**FastAPI** 是一个 Python 的 Web 框架，用处只有一句：把你写好的函数变成"网址能调用"的接口。端口、请求格式、返回值怎么序列化这些细节，它替你处理；你只要写好函数、说明它在哪个路径上，剩下的它包了——包括自动生成一个能点着试的测试页面，就是第 4 步会打开的 `/docs`。

**JSON** 是一种表示"有结构的数据"的文本格式，规则只有两条：`{}` 里放"键: 值"，`[]` 里放一串东西。像这样：

```json
{"file": "a.txt", "blocks": [{"text": "第一行", "locator": {"line": 1}}]}
```

它长得几乎和 Python 的字典、列表一样，区别是键必须用双引号、不能写注释。选它是因为几乎所有语言和工具都认：接口返回它，第 5 周的前端读它，存成文件用记事本也能看。

这两样都只是"载体"，不是这周的重点。重点是那份数据结构——同样的内容，从 txt 进来和从 md 进来，出去必须是同一个形状。

**这周不做什么。**记住一句就够：这周只负责"读进来"，不负责"读懂"。从文件里认出"哪个数字是财政收入"，是第 3 周的事；把它填进模板，是第 4 周的事；做成页面，是第 5 周的事。如果有人这周就开始调模型、写前端，多半两头都做不实——第一周那种"先把地基打平"的耐心，这周同样需要。

**关于两档。**上周不分档，因为环境和仓库是所有人的地基。从这周起分两档：第一档只做第一档那部分，步骤和命令写全，照着做就能交；第二档在它之上再加一段增量，先把第一档完整走一遍，再完成增量——那一段只给目标、方向和验收标准，没有步骤，怎么做由你自己规划。打算挑战第二档的同学，这周就开始。

**怎么算这周做成了？**不看"我跑通了一个文件"，看三件事：同一批文件跑两遍，结果一样；每个文件都能报出它被处理成了多少内容、花了多久；给一个坏文件，程序不崩，还能说清为什么。这三件听着朴素，但第 6 周"换台机器复现同样的数字"就是从这里长出来的——现在不记这些数，六周后补不回来。

还有一件事得提前说清楚，它决定你这六周过得顺不顺：**写代码不是先把知识学完再动手。**你不需要把 Python 从头学到尾、把几个库的文档读完，再来写这周的东西——那样永远开不了工。真实的做法是边写边学：先让最小的一个文件能被读出来，卡住了去查，查到的东西当场用上，用通了再往前走一步。报错、读不出内容、看不懂的参数，这周每天都会遇到，这跟你学得好不好没关系。你只要**带着具体的问题去搜**——把报错原文、把你在做什么、把已经试过什么一起贴进去，这类问题前人几乎都踩过，基本搜得到答案。

最后说时间和心态。上周大半时间花在装环境，这周会真正坐下来写代码，所以进度看起来会慢一些。卡过半小时，就按文末「卡住怎么办」做，别一个人硬扛。还有一句上周说过、这周更要紧的：可以让 AI 帮你写，但讲不清的代码留不下来——第 6 周交叉验收会指着代码问"这行为什么这么写"。

这周的产出会原样成为第 3 周的输入。这周图省事，把整篇原文囫囵塞成一个字符串，下周抽出一条数字时就答不出"它来自哪一句"，那时候返工，比现在多想一步要多花好几倍时间。

# 第二周任务（第一档 · 引导档）

## 目标

第一档要做成的事只有一件：**文本文件进来，出去是同一种结构。**

具体到可以检查的程度，是三条：

1. 一个接口，上传 `.txt` 或 `.md`，返回一份同形状的 JSON。
2. JSON 里每一块内容，都能说清它来自哪个文件、在第几行。
3. 同一批文件跑两遍，块数一模一样；喂一个坏文件，程序不崩，还能说清为什么。

## 任务清单

先把路线说清楚：

装依赖 → 找样例 → 定结构（`schema.py`）→ 写解析器（`parser_text.py`）→ 接口（`main.py`）→ 自测与留证。

顺序不要打乱。结构没定就先去写解析器，等这周第二档补上 docx、xlsx 时，仓库里会长出第二套字段。

每一步末尾都有"做完你应该看到什么"。别攒到最后一起验，一步一验，出错时才知道是哪一步的问题。

### 第 1 步：放进 doc 文件夹，找到两份样例文件，建好 data/ 目录

这周会发一个 `doc/` 文件夹，里面是整周要用的输入。先把它整个复制进仓库根目录，与 `backend/` 同级，不要放在 `backend/` 里面，也不要解压进某个子文件夹。放好后在仓库根目录验证一下（cmd 用 `dir doc`）：


应能看到 `DOCX`、`Markdown`、`TXT`、`XLSX` 四个子目录。看不到就是层级多套了一层，比如变成了 `doc/doc/02_输入样本`——这是复制文件夹最常见的失误，挪回来即可。里面的文件不要改名、不要增删：数字要跟别人可比，靠的就是同一批文件。

测试用的文件都在仓库的 `doc/02_输入样本/` 里。上传时在 `/docs` 页面选它们，写脚本时也按这个路径读。第一档先用这两份：

| 格式  | 用哪份                                           | 它的特点            |
| --- | --------------------------------------------- | --------------- |

另外在 `backend/` 里新建一个文件夹，命名为 `data`，这周接口输出的 JSON 就放在这里（此时它是空的）。

### 第 2 步：先把"数据长什么样"定下来

`schema.py` 只干一件事：定义形状，不读任何文件。解析器的输出必须符合它。

| 字段                 | 含义                        |
| ------------------ | ------------------------- |
| `file`             | 这份数据来自哪个文件（文件名，带后缀）       |
| `blocks[].type`    | 这一块是什么，这一档统一用 `text_line` |
| `blocks[].text`    | 这一行的文字                    |
| `blocks[].locator` | 它在原文第几行，记成 `{"line": 17}` |

这四个名字是推荐的写法，不是规定：你可以照用，也可以按自己的习惯改名（比如把 `file` 写成 `doc_name`）。唯一的硬要求是**解析器和接口用同一套**——改 `schema.py` 就一起改。

也没放 `ext`、`size`、`index` 这类字段，原因各一条：文件名已经带后缀，格式信息不必再存一遍；数组下标本身就是序号，多存一份就多一处会对不上的地方。

示例代码如下，整段存成 `backend/schema.py` 就能直接跑：

```python
# schema.py
# 这周的数据形状就定义在这两个类里，解析器返回 ParsedDoc。
# 字段名是推荐写法，改了就一起改。

from pydantic import BaseModel


class Block(BaseModel):
    """一个内容块，这一档里就是文本中的一行。"""

    type: str  # 这一档统一 text_line
    text: str
    locator: dict  # 它在原文的位置，这一档记 {"line": 行号}


class ParsedDoc(BaseModel):
    """一份文件的解析结果。"""

    file: str
    blocks: list[Block]


if __name__ == "__main__":
    # 手工拼一份最小结果，先确认形状：python schema.py
    demo = ParsedDoc(
        file="02_药品流通行业运行统计分析报告_2024.txt",
        blocks=[
            Block(
                type="text_line",
                text="2024年药品流通行业运行统计分析报告",
                locator={"line": 1},
            ),
            Block(type="text_line", text="一、发展概况", locator={"line": 2}),
        ],
    )
    print(demo.model_dump_json(indent=2))
```

`BaseModel` 是 pydantic 提供的模型基类，pydantic 随 FastAPI 一起装好了，不用另装。它带来的好处很实际：字段名写错、少写一个字段、把 `blocks` 写成字符串，创建对象时立刻报错，而不是等到后面填表才发现少了一半数据。

在 `backend/` 下运行：

```
python schema.py
```

打印出一份缩进好的 JSON，内容形如：

```json
{
  "file": "02_药品流通行业运行统计分析报告_2024.txt",
  "blocks": [
    {"type": "text_line", "text": "2024年药品流通行业运行统计分析报告", "locator": {"line": 1}},
    {"type": "text_line", "text": "一、发展概况", "locator": {"line": 2}}
  ]
}
```

最后把一条约定写进文件顶部的注释：**解析函数接收 bytes，返回 `ParsedDoc`**。这样接口那边把上传内容读出来直接传进去就行，本地测试用 `open(path, "rb").read()` 也一样能调。

**做完你应该看到**：`python schema.py` 打印出一份 JSON，顶层是 `file` 和 `blocks`，`blocks` 里每一项都带 `type`、`text`、`locator`。

### 第 3 步：写 txt / md 解析器

第一档唯一要你自己写的解析逻辑，就在这里。两种格式共用一个函数：把文件读成文本，**按换行符切开**，每一行一块。

新建 `backend/parser_text.py`——文件名照上面结构表里那个写，第 4 步的 `main.py` 就是按这个名字导入的，自己换成别的名字会导入失败。把下面这段抄进去，再把循环体按注释补齐（注释里那四行就是循环体，去掉行首的 `#` 即可）：

```python
from schema import Block, ParsedDoc


def parse_text(data: bytes, filename: str):
    text = data.decode("utf-8")
    blocks = []

    # 按换行符切（splitlines），跳过空行，每行一个 Block：
    # for i, line in enumerate(text.splitlines(), start=1):
    #     line = line.strip()
    #     if line:
    #         blocks.append(Block(type="text_line", text=line, locator={"line": i}))

    return ParsedDoc(file=filename, blocks=blocks)
```

为什么是按换行切、不是按空行分段：这两份样例里，txt 那份一个空行都没有，按空行切整篇只会剩 1 块；而每一行本来就是完整的一段，没有在句子中间折断的地方。

三件事容易写错，写完对一遍：

- **行号从 1 开始**。`enumerate(..., start=1)`，因为你在编辑器里看到的第 1 行就是第 1 行，别让它从 0 起。
- **先 `strip()` 再判空**。md 那份 120 行里有 52 行是纯空行，第 3 行行尾还带着空格；不 strip 直接判 `if line:`，这类纯空白行会被当成内容收进去。这份样例里恰好没有「只含空格、没有别的字符」的行，但换一份文件就有——按 strip 之后判空写，两种情况都不用改代码。
- **顺序不要动**。`splitlines()` 给什么顺序就按什么顺序 `append`，别去排序、别去重，第 3 周要靠行号回原文核对。

> md 不用解析语法：`#`、`**`、反引号这些标记原样留在文本里，这一档不处理，等第 3 周抽取时再决定怎么处理。


### 第 4 步：把解析器挂到接口上

`main.py` 只做四件事：收文件、看后缀、交给解析器、返回。这里没有业务判断，是纯接线。**下面这段是示例代码**，可以直接照抄，也可以按自己的习惯改写；真正要你自己写的是上一步的解析器。

```python
from fastapi import FastAPI, HTTPException, UploadFile

from parser_text import parse_text

app = FastAPI()


@app.post("/parse")
async def parse(file: UploadFile):
    data = await file.read()
    name = file.filename or ""
    ext = name.rsplit(".", 1)[-1].lower() if "." in name else ""

    try:
        if ext in ("txt", "md"):
            return parse_text(data, name)
    except Exception as exc:
        raise HTTPException(status_code=400, detail=f"解析失败：{exc}")

    raise HTTPException(status_code=400, detail=f"暂不支持的文件类型：{ext or '未知'}")
```

那个 `try/except` 别省：编码不对的文件会让 `decode` 直接抛异常，没有它，页面上只会看到一个 500，说不清是什么问题。


## 第二段：增量任务

### 目标

让同一份 `ParsedDoc` 装得下另外两类内容：docx 的段落与表格、xlsx 的表行。接口对 txt、md、docx、xlsx 四种格式都返回 200，其余仍是 400。

约束有两条：

1. **txt 与 md 的输出不能变**——块数还是 70 和 68，字段还是那三个。
2. **每个块的 `locator` 必须能唯一定位到原文的一处**——不同类型的块不要用同一个键名表达不同含义。比如都写成 `{"index": 3}`，一个指第 3 段、一个指第 3 张表，两条数据放在一起就分不清了。

测试文件仍取 `doc/02_输入样本/`：docx 用 `DOCX/05_南京市国民经济和社会发展统计公报_2021-2024.docx`（18 张表），xlsx 用 `XLSX/05_COVID-19全球数据集_节选.xlsx`（`max_row` 38473 行，含带格式的空行；有值的约一万五千行）。同一个仓库、同一批文件，数字才有可比性。

### 难度在哪里

真正难的不是"再多写两个解析器"，而是下面四件事：

- **结构要扩，但不能扩成两套。**表格的位置是"第几个表、第几行、第几列"，二维；你手上只有一维的行号。怎么让同一个字段同时表达这两种位置，是这个增量里唯一需要设计的地方。
- **docx 的段落与表格是两套集合。**分别遍历，原文顺序就丢了。保不保顺序是个取舍：保，要额外想办法；不保，要在 README 里写清代价。两种都能接受，但得有理由。
- **xlsx 是二维大表。**最大那份 `max_row` 38473 行、15 列（`A` 到 `O`），但有值的只有一万五千行左右——`max_row` 含大量带格式的空行，用它估工作量会高估一倍多。一次全读进内存这条路径人人想得到，但它会走得很吃力。
- **验收比实现难。**块数变多了，可"多"不等于"对"。你得能说清每类内容各有多少块、有没有哪一类被整类漏掉。

### 方向提示

下面只给方向，不给路径。

- **结构**：想清楚"位置"这一层要表达几种形态，再决定是扩 `locator` 的键，还是引入新的 `type`。判断标准只有一条：txt / md 的输出原样不动。
- **docx**：python-docx 的官方文档里，关于段落与表格是两组对象、以及如何按文档顺序遍历，写得比任何教程都清楚；顺序取舍的代价也在那里能想明白。
- **xlsx**：openpyxl 文档的 "Optimised Modes" 一节，讲的正是大文件读取这个场景，值得一读。
- **依赖**：这层要多装两个库（`python-docx`、`openpyxl`）。装法你在第一档已经用过两次，conda 用户注意包名与导入名的对应关系。
- **分派**：接口里已经有按后缀分派的写法，四种格式的支持清单应收在一处，别散到三四个地方。
- **自测**：第一档那个自测脚本可以扩成四份文件，仍然是跑两遍比对块数。

### 通过标准

# 卡住怎么办

**1、先看报错的最后一行。**

Python 的报错从下往上看最有效：最后一行是错误类型，上面几行是它发生在哪个文件、哪一行。类型决定方向——`ModuleNotFoundError` 是环境或目录问题，`UnicodeDecodeError` 是读文件编码问题，`ValidationError` 是数据结构没对上，`PackageNotFoundError` 是文件本身不是 docx。

**2、`ModuleNotFoundError: No module named 'schema'` 多半不是没装包。**

`schema.py` 是你自己写的文件，只有当前目录是 `backend/` 时 Python 才找得到它。先 `cd` 回 `backend/` 再跑；确认办法是 `dir` 一下能看到 `schema.py`。同理，`check.py` 里那句 `../doc/...` 也只有在 `backend/` 下执行才成立。

**3、块数不是 70 / 68 时，先把前三条打印出来看。**

三种典型症状，一眼能分辨：整篇只有 1 块——按空行切了；块数等于总行数（md 是 120）——没跳过空行；每块都是一大段——没按换行切。打印 `doc.blocks[:3]` 对照原文前三行，比盯着数字猜快得多。

**4、30 分钟没有进展，就把三句话整理好再问。**

"我在做什么、报错原文是什么、我已经试过什么"。报错要贴完整文字，不要只贴截图一角——文字能被搜索、能被 AI 读懂，截图不能。90% 的报错前人都踩过，原样搜基本搜得到。

**5、第二档遇到 docx / xlsx 的报错，先把例子缩到最小。**
