## 在新机器复现

要求 Python 3.14、Node.js `^22.18.0 || >=24.12.0` 与 npm。下列命令在仓库根目录运行；Windows 的对应命令见 README。**先构建前端，再导入后端测试模块**，因为 FastAPI 导入时会检查 `frontend/dist`。

```sh
python3.14 -m venv .venv
.venv/bin/python -m pip install -r backend/requirements.txt
(cd frontend && npm ci && npm run build)
.venv/bin/python -m pytest -q backend
.venv/bin/python backend/verify.py
```

公开样本只有跟踪的 `dataset/测试集.zip` 时也能验收；不要依赖本机预解压的 `dataset/测试集/`。以下两套数据库与源文件均位于临时目录，不调用 DeepSeek：

```sh
work_a23=$(mktemp -d)
.venv/bin/python backend/unpack_dataset.py --output "$work_a23/corpus"
.venv/bin/python backend/check_dataset.py --root "$work_a23/corpus" --data-dir "$work_a23/same" \
  --archived-facts backend/data/deliverables/source/city-original-historical.json
.venv/bin/python backend/check_dataset.py --root "$work_a23/corpus" --data-dir "$work_a23/same"
.venv/bin/python backend/check_dataset.py --root "$work_a23/corpus" --data-dir "$work_a23/rebuilt" \
  --archived-facts backend/data/deliverables/source/city-rebuilt-historical.json
.venv/bin/python backend/verify.py --same-db-dir "$work_a23/same" \
  --rebuilt-data-dir "$work_a23/rebuilt" --rebuilt-kind history
```

## 开发和 review 时的边界

- **先判断证据类型。** 合成模型替身证明程序行为；公开 01/03 的 `independent-source-check` 证明与公开原文的一致性；历史重建使用已有事实留档。正式参考表、语义金标和五套正式模板目前没有在仓库中形成可核验成绩。不得把上述测试写成正式准确率或正式 90 秒达标。
- **保护来源与版本。** 修改 `Store`、抽取发布、填表或评分时，检查原文块定位、文档 SHA-256、事实发布号、结果 ID 与工作簿摘要是否指向同一批。跨文档计划必须只使用所选资料；Word/Excel 目标值和逐格报告需共同回读。可参照 `backend/test_task_consistency.py`、`test_followup_audit.py` 和 `test_scoped_template.py`。
- **外部调用单列。** `backend/.env`、数据库、预解压目录和构建产物均不进 Git。新的真实 DeepSeek 实验会发送文件并计费，须取得针对本轮数据及请求量的明确授权；现有模型替身和历史响应可离线复验。
- **保持两类文档的 Git 边界。** 此交接文档和产品说明应跟踪；逐轮 code review、整改完成报告和隐私材料按 AGENTS.md 排除。提交前用 `git status --short`、`git diff --check`、`git ls-files` 和必要的密钥扫描核对。
- **独立验收。** 开发前提交基线，修改后从干净 Git 副本叠加补丁，按 README 构建并运行全量测试、`verify.py` 与相关定向用例。回归失败先定位是代码、材料、环境还是缺少正式证据；不要直接更新判据使失败消失。
